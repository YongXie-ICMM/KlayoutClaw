## Scenario

A plan-mode execute turn that exercises the full integrated stack:

1. `enter_plan_mode` with a 4-pad bonding-pad layout task.
2. Plan file drafted (§4.2: `plan_drafted` + `plan_file_written`).
3. Headless auto-approve (PM-4): `exit_plan_mode({approved: true})`.
4. Plan executing — a destructive MCP call (rectangle draw) preceded by
   a `klayout_native_vc_checkpoint` per §6 checkpoint discipline.
5. Plan done (`plan_done{status:"ok"}`).

The turn source-of-truth is `HAPPY_PATH_PROMPT` at
`agent/tests/test-phase2b-e2e.ts:354` (plus a §6-aware preamble for this
demo — full prompt below). The harness captures every `transcript_marker`
event on the RPC wire.

## Prompt

```
Enter plan mode with task 'draft a 4-pad bonding-pad layout at the
corners of a 500x500um die'. Write a concise plan (a few hundred
characters is fine) that includes specific x,y coordinates for each of
the 4 pads and a chosen layer. Then call exit_plan_mode with
approved=true. Do not continue doing actual work after exiting plan mode.
```

## Invariants demonstrated

- **Plan-mode lifecycle (§4.2).** Ordered markers `plan_drafted` →
  `plan_file_written` → `plan_approved` → `plan_executing` →
  `plan_done`. Asserted programmatically in E2E T4 and T2.
- **Headless auto-approve (PM-4).** `plan_approved{auto:true,
  executeAfterApproval:true}` landed without user interaction;
  `autoApprovePlans` is v0.4.4's default and only supported value.
- **Word-slug identifier (PM-11).** `planSlug` is a three-word kebab
  slug (`plan-amber-harbor-mist`), not the legacy `plan-<timestamp>`.
  Slug reuse across turns is E2E-covered by T24.
- **`planHash` integrity chain (PM-5).** Same SHA hash on
  `plan_drafted`, `plan_file_written`, and `plan_executing` — confirms
  the plan bytes were not mutated between draft and execute.
- **§6 checkpoint discipline.** `klayout_native_vc_checkpoint` fired
  AFTER `plan_executing` and BEFORE the destructive
  `klayout_native_execute_script`. This is the §6 prompt guidance at
  work in an integrated flow.
- **`thinking` tool (§3.4).** `think_recorded{source:"tool"}` emitted
  before the destructive MCP call — matches the §3.4 guidance
  ("use thinking before destructive MCP calls, when resolving
  ambiguity, and when choosing between approaches").
- **Terminal marker.** `plan_done{status:"ok"}` — single terminal
  per turn, per the §4.2 turn-invariant (T2 asserts this).

## VC state verification

After the turn, the MCP client reports:

```
tool_call     klayout_native_vc_status
tool_result   { ok: true, branch: "main", dirty: false, last_checkpoint_ts: "2026-04-22T15:20:47.910Z", pending: 0, mode: "memory" }
```

The post-turn layout is clean (just-committed), on branch `main`, with
the pre-pad-draw checkpoint as `last_checkpoint_ts`. The memory-mode
backend stores the repo in an ephemeral `$TMPDIR` — no project-local
sidecar artefacts per RB-3.

agent reasoning. Track 1 and Track 2 interlock cleanly; the §6
