# qlaybot v0.4.4 — Manual End-to-End Smoke Test Guide

> **Purpose:** walk a human operator through hands-on verification of every v0.4.4 feature after `python install.py` + KLayout launch. This is the companion to the automated gate (`docs/2026-04-22-qlaybot-v0.4.4-release.md` for the test-suite receipts; `docs/2026-04-22-qlaybot-v0.4.4-live-demo.md` for the G8-captured integrated transcript). Use this doc when you want to personally confirm each surface behaves as the spec says — before a demo, before pushing the release tag, or after a fresh machine install.
>
> **Expected runtime:** ~30 min end-to-end if everything works; longer if you want to exercise the edge cases.

---

## 0 · Prerequisites (one-time per machine)

### 0.1 Environment

```bash
# Conda env with the subprocess deps used by auto_route + evaluate_design + VC serializer
conda activate base   # or instrMCPdev if you have it; both work per G5 memory
python -c "import numpy, scipy, skimage, gdstk, cv2, klayout.db as pya; print('OK')"
```

### 0.2 Anthropic API key

```bash
export ANTHROPIC_API_KEY=...
```

Required for any agent-driven section (Parts 1, 2, 4). Pure plugin tests (Part 3's UI clicks) do not need it.

### 0.3 Install the plugin

```bash
cd ~/testFolder/KlayoutClaw
python install.py
```

Expected output includes:

```
plugin/klayoutclaw_server.lym   → ~/.klayout/pymacros/klayoutclaw_server.lym
plugin/klayoutclaw_ui.lym       → ~/.klayout/pymacros/klayoutclaw_ui.lym
plugin/klayoutclaw_vc/          → ~/.klayout/pymacros/klayoutclaw_vc/
tools/vc_mcp_handlers.py        → ~/.klayout/pymacros/tools/vc_mcp_handlers.py
```

If any of the four lines is missing, the install script is out of date; re-run after pulling. Abort and fix before continuing.

### 0.4 Launch KLayout fresh

```bash
# Kill any running KLayout first (new plugin won't register otherwise)
pkill -f klayout ; sleep 2
open /Applications/klayout.app
```

Wait ~5s for Qt to spin up. You should see the KLayout main window with an empty workspace.

### 0.5 Verify MCP server is up

In a terminal (not inside KLayout), run:

```bash
curl -s -X POST http://127.0.0.1:8765/mcp \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  | jq '.result.tools | length'
```

**Expected: `19`** (10 v0.4.3 tools + 9 `vc_*` tools new in v0.4.4).

If you get `10` → the `vc_*` plugin didn't load; check KLayout's macro log for import errors on `klayoutclaw_vc`.
If you get a connection error → KLayout isn't running, or the MCP macro isn't in `~/.klayout/pymacros/`.
If you get `11` or anything between 10 and 19 → partial VC registration; check the LYM for a syntax error.

### 0.6 Start the qlaybot agent

```bash
cd ~/testFolder/KlayoutClaw/agent
npm install   # only needed first time
npm run build # only if you have local TS changes
npm start     # launches the interactive TUI
```

Expected first-frame output: qlaybot banner + `❯` prompt ready. If you see `MCP server connection failed`, re-check Step 0.5.

You now have everything you need. Proceed to Parts 1–4 in order.

## Part 1 · `thinking` tool (Feature 1)

**Spec anchor:** §3 entirely. Requirements TH-1 through TH-14.

**Goal:** prove the agent has a side-effect-free scratchpad tool that externalises reasoning, surfaces transparently in the TUI, and doesn't interfere with native Anthropic thinking blocks.

### 1.1 `thinking` appears in `tools/list` (TH-1, TH-4)

In the agent, type:

```
/mcp tools
```

Scroll the list. Expected entries (among others):

- `thinking` — top-level, NO prefix, description starts with "Record a reasoning step."
- `klayout_native_create_layout`, `klayout_native_execute_script`, `klayout_native_auto_route`, `klayout_native_evaluate_design`, `klayout_native_save_layout`, `klayout_native_get_layout_info`, `klayout_native_screenshot`, `klayout_native_route_inspect`, `klayout_native_validate_pixel_size`, `klayout_native_close_layout_view`
- `klayout_native_vc_init`, `klayout_native_vc_checkpoint`, `klayout_native_vc_history`, `klayout_native_vc_checkout`, `klayout_native_vc_diff`, `klayout_native_vc_branch`, `klayout_native_vc_tag`, `klayout_native_vc_export`, `klayout_native_vc_status`

Total count: **19 + `thinking` + other agent built-ins (read, bash, edit, write, memory_*, delegate, enter_plan_mode, exit_plan_mode)**.

**Verify:** `thinking` is present, has no prefix, and `tools/list` shows 19 `klayout_*` entries. If `thinking` is missing → §3 wiring broken (check `agent/src/tools/index.ts` registration).

### 1.2 `thinking` is a no-op echo (TH-3)

Prompt in the agent:

```
Call the thinking tool with the argument thought: "testing the tool returns the thought verbatim"
```

Expected:
- A visible tool call event in the TUI.
- The tool result contains the input `thought` string byte-for-byte.
- The TUI's thinking panel shows the text with **a theme color distinct from native thinking blocks** (TH-6 / TH-9: `source="tool"` vs `source="native"`).
- No filesystem write, no MCP call, no layout mutation.

**Verify:** `cat ~/.qlaybot/history/$(date +%Y-%m-%d)/latest/*.jsonl | grep think_recorded | tail -1 | jq '.data.source'` → returns `"tool"`.

### 1.3 `thinking` before destructive MCP (TH-5, prompt guidance)

Give the agent a task that forces a destructive call:

```
Use execute_script to create a cell named "test_manual" with a single 10 µm × 10 µm polygon on layer 1/0. Before you do, note your intent.
```

Expected:
- At least one `think_recorded` marker in the transcript before the `klayout_native_execute_script` call.
- The agent's reasoning mentions layer, geometry, or coordinates in the `thought`.

**Soft check — not a gate, but a behavior confirmation.** If no `thinking` call fires, the prompt guidance is being ignored; file a follow-up.

### 1.4 `thinking` coexistence with native Anthropic thinking (TH-9, T19)

The native-thinking surface is model-stochastic, so this is a best-effort verification:

```
/effort high
```

Then prompt:

```
Design question — before answering, reason carefully about trade-offs.
For a 4-probe Hall bar at 4K in a 10 T field, which lead geometry is best:
(A) 500 nm wide top-contact, (B) 250 nm wide side-contact,
(C) 1 µm square corner-contact, (D) 100 nm wide edge-contact?
Pick the best. You MUST call the thinking tool before giving the final answer.
```

Expected:
- Possibly a native `thinking` block (model's own chain-of-thought) — visible in the TUI with one theme color.
- A `thinking` tool call with the same turn — visible with a different theme color (TH-6).
- Neither is re-emitted as the other (TH-9 non-conflation).

**Note:** native-block emission is stochastic. If you don't see a native block, retry once; if still missing, this path is covered deterministically by `test-thinking-e2e.ts` T19(a-1)/(a-2) replay tests — not a release blocker (per the G8 audit decision documented in the release notes).

### Part 1 success criteria

- [ ] `thinking` listed in `/mcp tools`.
- [ ] 1.2 tool-result echoes the `thought` verbatim.
- [ ] 1.2 TUI renders with the "tool" theme color, not the native one.
- [ ] 1.3 agent calls `thinking` before geometry-mutating ops unprompted (soft).
- [ ] 1.4 neither native block is conflated with `think_recorded` marker in the same turn (best-effort).

## Part 2 · Plan-mode execution (Feature 2)

**Spec anchor:** §4 entirely. Requirements PM-1 through PM-14.

**Goal:** prove the four-option approval gate works interactively, the plan file is hashed and integrity-checked, the permission context swaps, the replan loop bounds failure, and the `autoApprovePlans: false` coercion warning fires in headless.

### 2.1 Happy-path plan-mode execution (T2)

In the agent, prompt:

```
Enter plan mode for this task: add 4 bonding pads at the corners of a 1 mm × 1 mm die on layer 2/0, pad size 100 µm × 100 µm.
```

Expected flow in the TUI:

1. Agent calls `enter_plan_mode({task: "...", reason: "..."})` → plan file created under `~/testFolder/KlayoutClaw/agent/plans/<word-slug>.md` (e.g. `brave-lantern.md`, NOT `plan-<timestamp>.md` — PM-11 refactor).
2. Agent reads current layout state via `klayout_native_get_layout_info` (read-only sandbox).
3. Agent writes the plan into the file using `write`/`edit` scoped to `<plansDir>/`.
4. Agent calls `exit_plan_mode({approved: true})`.
5. **The 4-option `PlanApprovalMenu` appears in the TUI** with:
   - `1. Approve & execute`
   - `2. Approve draft-only`
   - `3. Reject with feedback`
   - `4. Abandon`

**Verify the transcript markers** (in another terminal):

```bash
cat ~/.qlaybot/history/$(date +%Y-%m-%d)/latest/*.jsonl \
  | jq -r 'select(.type == "transcript_marker") | .data.type' | tail -20
```

Expected sequence:
```
plan_drafted
plan_file_written
```

Then after you press `1`:
```
plan_approved       # with auto:false, executeAfterApproval:true
plan_executing
```

And when the execution finishes:
```
plan_done           # with status:"ok"
```

**Verify hash chain (PM-5):**

```bash
cat ~/.qlaybot/history/$(date +%Y-%m-%d)/latest/*.jsonl \
  | jq -r 'select(.data.planHash) | .data.type + " " + .data.planHash' | tail -5
```

All three `planHash` values (on `plan_drafted`, `plan_file_written`, `plan_executing`) should be identical sha256 hex.

### 2.2 Test each of the 4 gate options

Run four independent sessions, one per option, and confirm the terminal markers:

| Option | Marker sequence to see | Turn ends on |
|---|---|---|
| `1 — Approve & execute` | `plan_drafted → plan_file_written → plan_approved{executeAfterApproval:true} → plan_executing → plan_done` | `plan_done` |
| `2 — Approve draft-only` | `plan_drafted → plan_file_written → plan_approved{executeAfterApproval:false}` | `plan_approved` (no `plan_executing`) |
| `3 — Reject with feedback` | `plan_drafted → plan_file_written → plan_rejected{action:"reject", feedback:"your text"} → plan_drafted …` | replan loop continues in same turn |
| `4 — Abandon` | `plan_rejected{action:"abandon", feedback:"abandoned"}` | immediate terminal |

**Invariant:** exactly one terminal marker per turn (§4.2). If you see two `plan_done` or `plan_done` + `plan_rejected`, something's wrong.

**Free-text affirmatives** for option 1: type any of `yes`, `y`, `go`, `/go`, `ok`, `okay`, `approved`, `approve` at the menu (case-insensitive). All should map to `approve_execute`.

**Anything else as free text** → counts as `reject` with the raw text as feedback.

### 2.3 Plan-file slug lifecycle (T24)

In the same `AgentSession`, do:

```
/plan enter design a simple Hall bar
(let it draft a bit, then)
/plan exit false   # abandon shortcut
/plan enter design a different Hall bar
```

**Expected:** the second `enter_plan_mode` generates a **fresh word slug** (different file name). Abandon clears the slug cache (PM-12).

Now try the truncation path:

```
/plan enter task X
(draft)
(approve & execute → plan_done)
/plan enter task Y
```

**Expected:** the second `enter_plan_mode` **reuses the same slug** but the plan file is truncated to 0 bytes first — no leakage from task X (PM-11 path 1.b, T24(d.3)). Verify:

```bash
cat agent/plans/<slug>.md   # right after the second enter_plan_mode
```

Should be empty (or contain only the agent's freshly-written first lines).

### 2.4 Hard freeze in `plan_drafted` (T36, PM-8)

Drive the flow manually to pause at `plan_drafted`:

```
/plan enter test hard freeze
(draft something brief)
/plan exit true   # triggers exit_plan_mode({approved:true})
```

**Before you press 1/2/3/4 at the approval menu**, the session is in `plan_drafted` state. In this state, **no tool calls fire** — including `thinking`. If the agent tries to call any tool, you should see a state-violation error `plan_state_frozen`.

**Hard to test from the TUI** (the gate blocks user input until decision). Alternative: use the JSON-RPC transport with a stubbed session — covered by the `test-plan-state-machine.ts` T36 unit test. For manual verification, just confirm the menu blocks indefinitely without side effects (no MCP calls visible in the transcript between `plan_drafted` and your decision).

### 2.5 Replan loop (T5)

Induce an unrecoverable failure. Easiest way:

```
Enter plan mode to auto_route between pin_a_layer L1 and pin_b_layer L2 where L1 and L2 are empty. Make that the whole plan.
```

Expected:
- Plan drafted + approved + executed.
- `klayout_native_auto_route` returns an error because there are no pins.
- Harness classifies the failure as unrecoverable per §4.5.
- Marker sequence: `plan_execution_aborted → plan_replan → plan_drafted → …` (replan attempt 1).
- After 3 failed replans, `plan_done{status: "failed", reason: ...}` with cumulative blocker history.

**Verify the cap** (attempt 4 → fail, not infinite):

```bash
cat ~/.qlaybot/history/$(date +%Y-%m-%d)/latest/*.jsonl \
  | jq -r 'select(.data.type == "plan_execution_aborted" or .data.type == "plan_replan" or .data.type == "plan_done") | .data.type' | tail -10
```

Count should be: 3× `plan_execution_aborted`, 3× `plan_replan`, 1× `plan_done{failed}` = 7 markers.

### 2.6 Headless `-m` auto-approve + `autoApprovePlans: false` coercion warning (T35, PM-4)

In a fresh terminal:

```bash
cd agent
npm start -- --headless --autoApprovePlans=false <<< '{"method":"prompt","params":{"text":"enter plan mode and draft a small task"}}'
```

Expected:
- Startup log contains a warning like `"autoApprovePlans=false is v0.4.5 (OQ-7); treating as true"`.
- `exit_plan_mode({approved: true})` auto-executes with `plan_approved{auto:true, executeAfterApproval:true}`.
- No gate menu opens (there is no gated-headless path in v0.4.4).

### Part 2 success criteria

- [ ] 2.1 happy path fires `plan_drafted → plan_file_written → plan_approved → plan_executing → plan_done` with matching `planHash` across all three.
- [ ] 2.2 all four gate options tested; each produces the documented marker trail; exactly one terminal marker per turn.
- [ ] 2.3 abandon path generates fresh slug; `plan_done` path reuses slug with file truncated.
- [ ] 2.4 no MCP calls between `plan_drafted` and decision.
- [ ] 2.5 replan cap = 3; 4th attempt emits terminal `plan_done{failed}`.
- [ ] 2.6 `autoApprovePlans: false` warning fires in headless, path coerces to `true`.

## Part 3 · KLayout version control (Feature 3)

**Spec anchor:** §5 entirely. Requirements VC-1..VC-7, DM-1..DM-5, RB-1..RB-4, UI-1..UI-5, MCP-1..MCP-9.

**Goal:** confirm the plugin-side Qt UI and the 9 `vc_*` MCP tools all work, both from the GUI and from the agent.

### 3.1 Create a layout and watch the status chip (UI-1, T25, T28)

In KLayout, `File → New Layout → Top Cell: TOP, DBU: 0.001, OK`.

Expected in the status bar (bottom of main window): a chip like `main • clean • last: 0 min ago`.

**Interpretation:**
- `main` — the initial git branch created for this unsaved layout (memory mode per RB-1; no sidecar on disk yet).
- `clean` — no unsaved edits since last checkpoint (vacuous initially).
- `last: 0 min ago` — timestamp of the last checkpoint (initial baseline).

Draw a polygon (any shape, any layer) using KLayout's tools. The chip should flip to **`⬤dirty`** within a few seconds (Qt timer polls `repo.status()`).

### 3.2 Checkpoint via hotkey (UI-2, T26)

Press `Ctrl+Shift+K`.

Expected: a modal dialog with:
- `Message:` text field (required)
- `Tags:` text field (optional, comma-separated)

Type `baseline` in Message, leave Tags empty, click **OK**.

Expected:
- Dialog closes.
- Status chip returns to `clean`.
- `last: 0 min ago` resets.

### 3.3 History dock panel (UI-3, T26)

Press `Ctrl+Shift+H`.

Expected: a dockable widget opens (usually right side) with a scrollable list. The top row should be the `baseline` commit you just made, showing:
- Timestamp (human-relative, e.g. "just now")
- Message: `baseline`
- Tags: (empty)
- Thumbnail: generated on-demand — may show briefly empty then populate.

Make 3 more edits + checkpoints with messages `"after move"`, `"after resize"`, `"after layer swap"`. Verify:
- Panel shows 4 rows, newest at top.
- Older rows' thumbnails are **NOT precomputed** — verify by closing/reopening the panel fast and noticing thumbnails load as rows become visible. (T26 explicit assertion.)

### 3.4 Save integration auto-checkpoint (UI-4, T27)

In KLayout, `File → Save As → test.gds`.

Expected:
- GDS file written.
- A new commit auto-lands in the history panel with message like `"auto-checkpoint on save"` (or similar, per impl).
- `test.gds.vc/` directory now exists **on disk** (memory mode migrated to disk per DM-4):

```bash
ls -la test.gds.vc/
# expect a valid git repo structure (HEAD, refs/, objects/, ...)
```

Toggle auto-checkpoint off (settings menu or config — check `settings.json` for `autoCheckpointOnSave`). Save again. Expected: GDS writes, but NO new commit in history.

Toggle back on for the rest of this manual.

### 3.5 Context menus (UI-5, T32 — **soft gate**)

- Right-click layout background (not on geometry) → context menu should contain `Checkpoint` entry that opens the Task 6.2 dialog.
- Right-click a row in the history panel → context menu should contain `Checkout`, `Branch from here`, `Tag` entries.

**If any of these don't appear or behave wrongly,** it's a soft-gate miss per §9.6 — documented as a known issue, not a release blocker.

### 3.6 MCP calls from the agent

Back in the qlaybot TUI, try each `vc_*` tool:

```
Call klayout_native_vc_status with no args.
```

Expected: `{ok: true, branch: "main", dirty: false, last_checkpoint_ts: ..., pending: [...], mode: "disk"}`.

```
Call klayout_native_vc_history with limit: 5.
```

Expected: array of the last 5 commits with `{sha, message, ts, tags, branch, stats: {polygon_count, layer_count, bbox}}`.

```
Call klayout_native_vc_diff with ref_a: HEAD~2 and ref_b: HEAD.
```

Expected: structured JSON with `added_polygons`, `removed_polygons`, `moved_polygons`, `layer_stats`, `bbox_delta`, `polygon_count_delta`.

```
Call klayout_native_vc_tag with name: "manual-test-tag".
```

Expected: `{ok: true}`. Verify with `klayout_native_vc_history`; the HEAD commit should now have `tags: ["manual-test-tag"]`.

```
Call klayout_native_vc_tag again with the same name.
```

Expected: `{ok: false, reason: /name already exists|tag collision/}` (T40 collision path).

```
Call klayout_native_vc_export with ref: HEAD and format: "pya".
```

Expected: either inline `{format: "pya", content: "<python code>", truncated: false}` for small layouts OR `{format: "pya", truncated: true, path: "/tmp/..."}` for large ones (T45 truncation).

### 3.7 Branch + merge (T12, T46)

```
Call klayout_native_vc_branch with op: "create", name: "experiment/wide-metal".
```

Then:

```
Call klayout_native_vc_branch with op: "switch", name: "experiment/wide-metal".
```

Make edits (e.g., widen a polygon), checkpoint via `Ctrl+Shift+K` with message `"widened"`.

Switch back:

```
Call klayout_native_vc_branch with op: "switch", name: "main".
```

Confirm widened polygon is absent (layout reverts). Switch back to the experiment branch — confirm presence.

**Merge conflict test (T46):** create branches `a` and `b` from HEAD, modify the same polygon differently on each, checkpoint each. Then merge `a` into `main` (succeeds), then merge `b`:

```
Call klayout_native_vc_branch with op: "merge", name: "b".
```

Expected: `{ok: false, conflicts: [{cell, layer, bbox}], ...}`. Neither `main` nor `b` should be mutated (verify via `vc_history`).

### 3.8 Graceful degradation (§8.3)

Close the current layout (`File → Close Layout`) so no `RepoHandle` is registered. Then:

```
Call klayout_native_vc_status with no args.
```

Expected: `{ok: false, reason: "vc not initialized"}`.

```
Call klayout_native_vc_checkpoint with message: "test".
```

Expected: same `{ok: false, reason: "vc not initialized"}` — the uninit fallthrough handles every `vc_*` tool except `vc_init` and `vc_status`.

```
Call klayout_native_vc_init with mode: "memory".
```

Expected: `{ok: true, mode: "memory"}`. Now subsequent `vc_*` calls work again.

### 3.9 Crash recovery (T15 — manual)

**Setup:**
1. Open an existing `.gds` with a `.gds.vc/` sidecar (one you saved in step 3.4).
2. Make a checkpoint A with a known polygon.
3. Make one further edit WITHOUT checkpointing.

**Kill KLayout hard:**

```bash
pkill -9 -f klayout
```

Wait 3s, relaunch:

```bash
open /Applications/klayout.app
```

Open the same `.gds`. Expected:
- Plugin detects `.gds.vc/RECOVERY/journal.json` references checkpoint A as last-known-good.
- A recovery dialog (or status chip annotation) offers to restore to A.
- On accept, layout is restored to checkpoint A's state.
- The post-A unchecked edit is **not** recovered (DM-5 scope is last-known-good, not arbitrary mid-edit state).

### Part 3 success criteria

- [ ] 3.1 status chip shows `branch • clean/dirty • last: N min ago` and updates on edit/checkpoint.
- [ ] 3.2 `Ctrl+Shift+K` opens dialog, submits, chip flips to clean.
- [ ] 3.3 `Ctrl+Shift+H` opens dock panel, newest commits on top, thumbnails lazy.
- [ ] 3.4 save triggers auto-checkpoint (on), `test.gds.vc/` appears on disk.
- [ ] 3.5 context menus render with Checkpoint / Checkout / Branch from here / Tag (soft).
- [ ] 3.6 `vc_status`, `vc_history`, `vc_diff`, `vc_tag`, `vc_export` all work from agent.
- [ ] 3.7 branch create/switch/merge happy path works; merge conflict returns structured `{ok:false, conflicts:[...]}`.
- [ ] 3.8 uninit fallthrough returns `{ok:false, reason:"vc not initialized"}` for every tool except `vc_init` and `vc_status`.
- [ ] 3.9 crash recovery dialog offers last-good checkpoint.

## Part 4 · Integrated cross-track flow (prompt-guided checkpoint + replan + VC recovery)

**Spec anchor:** §6 cross-track integration, T17, T18 (soft).

**Goal:** confirm the three features work together as designed — the agent consults the VC state during a plan-execute flow, checkpoints before destructive ops, and recovers on blocker.

### 4.1 The integrated prompt

With KLayout open on a layout that has an initialised VC repo (from Part 3), in the qlaybot TUI:

```
Design a Hall bar device with 4 bonding pads, route leads from contacts to pads with auto-routing, and evaluate the design. Use version control to checkpoint your work before any destructive step.
```

### 4.2 Expected sequence (T17 soft assertion)

Watch the transcript markers + tool calls:

1. `plan_drafted → plan_file_written → plan_approved{executeAfterApproval:true} → plan_executing`.
2. At least one `klayout_native_vc_checkpoint` call **before** the first destructive MCP call (`execute_script` or `auto_route`). Soft — a miss emits a warning, not a failure.
3. `think_recorded` markers describing the decisions (especially choice of routing strategy).
4. `klayout_native_auto_route` called with real pins.
5. `klayout_native_evaluate_design` called after routing.
6. `plan_done{status: "ok"}`.

Confirm in the history panel that new VC commits appeared during execution, with messages like `"before routing"` or `"pre-evaluation"`.

### 4.3 Recovery-on-blocker (T18 soft)

Intentionally break something. E.g., close the current layout mid-execution, or manually delete a cell the plan depends on. Re-prompt:

```
Continue the Hall bar design from where you left off. Recover from any blockers using version control.
```

Expected (soft): if the agent hits an unrecoverable blocker (classified per §4.5), it:
- Emits `plan_execution_aborted`.
- Ideally calls `klayout_native_vc_checkout` to revert to the last good state (soft assertion — a miss is a warning).
- Re-drafts the plan with updated context.
- Completes or exhausts the 3-replan cap.

### Part 4 success criteria

- [ ] 4.2 at least one `klayout_native_vc_checkpoint` fires before a destructive MCP call (soft).
- [ ] 4.2 final `plan_done{status: "ok"}` emitted.
- [ ] 4.3 agent attempts recovery via `vc_checkout` on blocker (soft).
