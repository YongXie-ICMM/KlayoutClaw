### Structural Parallel: instrMCP ↔ KLayout MCP

KLayout MCP in qlaybot occupies the same architectural position as instrMCP in qdevbot — it's the **primary domain-specific MCP server**. The config structure should mirror this:

| | qdevbot | qlaybot (proposed) |
|---|---|---|
| Domain MCP config file | `instrmcp.json` | `klayout.json` |
| Domain MCP URL | `http://localhost:8123/mcp` | `http://127.0.0.1:8765/mcp` |
| Disabled tools | `instrmcp.json → disabledTools[]` | `klayout.json → disabledTools[]` |
| Domain-specific settings | `instrmcp.json → paramFilter` | `klayout.json → autoLaunch, toolAnnotations` |
| Generic MCP servers | `mcp.json` | `mcp.json` |

This gives qlaybot the same **4-file config split** as qdevbot: `model.json`, `klayout.json`, `mcp.json`, `settings.json`.

## 2. Config System Upgrades

### 2.1 4-File Config Split

Align with qdevbot's 4-file pattern. Current qlaybot has 3 files (model, mcp, settings). Add a dedicated `klayout.json` for the domain MCP server:

| File | Content | Parallel in qdevbot |
|------|---------|---------------------|
| `model.json` | Providers (with apiKey + baseUrl), models, defaultModel, thinkingLevel | `model.json` |
| **`klayout.json`** (new) | KLayout MCP URL, `disabledTools[]`, `autoLaunch`, domain settings | `instrmcp.json` |
| `mcp.json` | Generic MCP servers (future extensibility) | `mcp.json` |
| `settings.json` | Memory, compaction, TUI, subagent (Spec 2), search + embedding (Spec 3) | `setting.json` |

**`klayout.json` schema:**
```json

  "required": true,

  "disabledTools": [],
  "_note": "KLayout MCP server — the primary domain MCP, analogous to instrMCP in qdevbot"
}
```

### 2.3 Config Save Functions

Currently config is read-only after init. Add save helpers for all 4 files:

```typescript
export function saveModelConfig(config: QlayBotConfig): void;
export function saveKLayoutConfig(config: QlayBotConfig): void;  // NEW
export function saveMCPConfig(config: QlayBotConfig): void;
export function saveSettingsConfig(config: QlayBotConfig): void;
```

Each reads the existing file, deep-merges the relevant section, and writes back. This replaces the ad-hoc `writeFileSync` in individual command handlers (`config.ts`, `model.ts`).

### 2.4 Config Load Migration

On load, migrate `klayout_mcp` out of `mcp.json`:
1. If `mcp.json` contains `klayout_mcp` entry:
   a. If `klayout.json` does not exist → write `klayout.json` from the extracted entry
   b. If `klayout.json` already exists → skip (don't overwrite)
   c. **Always delete `klayout_mcp` from `mcp.json`** and rewrite the file (prevents stale key persisting through deep-merge)
2. Log migration message

This runs on every load (idempotent) — if `klayout_mcp` is gone, step 1 is a no-op. The save helpers' deep-merge will never re-introduce `klayout_mcp` because no code path writes to that key anymore.

This mirrors qdevbot's `splitOldConfig()` pattern.

**Interaction with SETUP wizard**: The wizard calls `initializeUserDir()` first (which may write old-style `mcp.json` with `klayout_mcp`), then `loadConfig()` runs migration before the wizard overwrites config with collected values. Order: `initializeUserDir()` → `loadConfig()` (migrates) → wizard saves → session starts.

Additionally, migrate bare model IDs to provider-prefixed format:
- If `defaultModel` is `"claude-sonnet-4-6"` (no `/`), rewrite to `"custom-anthropic/claude-sonnet-4-6"`
- Log migration message
- This ensures the 5-step model resolver (section 2.5) always gets an explicit provider

### 2.5 Multi-Provider Model Resolution

Port qdevbot's 5-step model resolver:

1. **Exact match**: `provider/modelId` in configured providers
2. **Any-provider match**: search `modelId` across all providers
3. **Prefix match**: e.g., `"claude-sonnet-4-6"` matches `"claude-sonnet-4-6-20250929"`
4. **First model fallback**: first model from first provider
5. **Error**: no model found

Add `resolveModel(config, ref)` function in `config.ts`. Used by `createDesignSession()` and `/model set`.

## 3. SETUP Wizard

### 3.1 Trigger

When `isInitialized()` returns `false` at startup, the SETUP wizard runs **instead of** the current `initializeUserDir()` call. The existing auto-initialize path in `createDesignSession()` must be removed — `cli.ts` now gates on `isInitialized()` and either runs the wizard (interactive mode) or calls `initializeUserDir()` with defaults (non-interactive JSON/RPC modes where no TUI is available).

```typescript
// cli.ts — before createDesignSession():
if (!isInitialized()) {
  if (mode === "interactive") {
    const config = await runSetupWizard();  // TUI wizard
    // session uses returned config
  } else {
    initializeUserDir(templateDir);  // silent defaults for RPC/JSON mode
  }
}
```

### 3.2 Flow (6 Steps)

Rendered as a dedicated Ink component (`SetupWizard.tsx`) — **not** reusing InputBox, since the wizard needs a masked input mode that InputBox doesn't support. The wizard component has its own `useInput` handler with step-based state machine:

1. **Welcome** — Display qlaybot version, purpose. Press Enter to continue.
2. **API Key** — Prompt for API key. Input renders each character as `*` (masked mode). If `ANTHROPIC_API_KEY` env var is already set, show `[env: ****...****]` and offer to use it (Enter to accept, or type to override). Validate by attempting a lightweight API call.
3. **Model Selection** — Show numbered list of available models (from default provider config). User picks default model by number or Enter for recommended (Sonnet 4.6).
4. **MCP Servers** — Auto-detect KLayout at `:8765` (HTTP health check). Show detected servers. Offer to add custom MCP server URL. Enter to accept defaults.
5. **Vector Search (optional, from Spec 3)** — "Enable semantic vector search? Requires an embedding API (e.g., OpenAI text-embedding-3-small). Enter base URL and API key, or press Enter to skip." If provided, populates `embedding.*` and sets `search.mode` based on available providers:
   - If an Anthropic provider is configured (step 2) → `search.mode = "fts5+vector+rerank"`
   - If only non-Anthropic providers → `search.mode = "fts5"` with a note: "Reranking requires an Anthropic provider. Vector search will be available once you add one."
   - If skipped → `search.mode` stays `"fts5"`
6. **Confirm & Write** — Summary of choices. Enter to write config files via save functions and start session.

### 3.3 Implementation

New files:
- `agent/src/setup.ts` — wizard logic and config assembly
- `src/tui/components/SetupWizard.tsx` — Ink component with masked input + step state machine

```typescript
// setup.ts
export async function runSetupWizard(): Promise<QlayBotConfig>;
```

Called from `cli.ts` before `createDesignSession()`. Returns the config to use for the session. Writes files via the new save functions.

The wizard renders as a standalone Ink app (not inside the main App component). After completion, the main App mounts with the returned config.

**Important**: The wizard must also copy workspace templates (including `workspace/subagent/*.md` prompt files from Spec 2) via the same template-copy logic as the current `initializeUserDir()`. This ensures subagent roles have their prompt files available on first run. The wizard calls `initializeUserDir(templateDir)` for directory/template setup, then overwrites config files with wizard-collected values.

### 3.4 Entry Points & Re-run

Three ways to enter the SETUP wizard:

1. **Auto first-run**: `cli.ts` gates on `isInitialized()` — if false and interactive mode, wizard runs automatically before session starts
2. **`qlaybot setup`**: New CLI command that runs the wizard directly (also `qlaybot onboard` as backward-compatible alias). `cli.ts` commands become: `run | onboard | setup | uninstall | help | slash`
3. **`/config setup`**: TUI slash command re-runs the wizard (backs up existing config first). Available inside a running session.

## 4. Inline Ghost Text Hints

### 4.1 Behavior

When the user types a `/` prefix in InputBox:
- If exactly **one** command matches, show the remaining suffix as dimmed gray text after the cursor
- If **multiple** match, show the suffix of the **most recently used** matching command as dimmed ghost text. Up/Down arrows open the CompletionList dropdown for browsing alternatives (see §4.4). The ghost hint gives a quick preview of the likely intent.
- If **no** match, show nothing

Examples:
- `/mo` → ghost: `del` (only match, no `↑` — nothing to browse)
- `/co` → ghost: `nfig↑` if `/config` was used more recently than `/compact`
- `/co` → ghost: `mpact↑` if `/compact` was used more recently
- Tab while ghost is showing → accepts the ghost hint (auto-completes the command)
- Up/Down arrows while CompletionList is open → navigate through matches, ghost text updates to selected item

The `↑` suffix appears **only when multiple commands match**, hinting that arrow keys can browse alternatives. Single-match ghost text has no arrow — there's nothing else to pick.

### 4.2 Command Recency Tracking

Add a `commandRecency: Map<string, number>` to track when each command was last used. Updated on every command submission in `handleSubmit()`:

```typescript
// In InputBox or App.tsx, on submit:
if (text.startsWith("/")) {
  const cmd = text.split(/\s/)[0];  // e.g., "/config"
  commandRecency.set(cmd, Date.now());
}
```

Persisted in `~/.qlaybot/history.json`. **Note**: The current `useCommandHistory` hook starts with an empty array each run and does not load from disk. This must be fixed as part of this feature:
1. Extend `history.json` schema to include `{ entries: string[], recency: Record<string, number> }`
2. `useCommandHistory` loads entries + recency on mount, saves on update
3. Backward compat: if `history.json` is an array (old format), migrate to `{ entries: [...], recency: {} }`

### 4.3 Implementation

In `InputBox.tsx`:

```tsx
function getGhostSuffix(value: string, recency: Map<string, number>): string {
  if (!value.startsWith("/")) return "";
  const matches = matchCommands(value.trimEnd());
  if (matches.length === 0) return "";
  if (matches.length === 1) {
    return matches[0].slice(value.trimEnd().length);
  }
  // Multiple matches: pick most recently used
  const sorted = [...matches].sort((a, b) =>
    (recency.get(a) ?? 0) - (recency.get(b) ?? 0)
  );
  const best = sorted[sorted.length - 1];  // highest timestamp = most recent
  return best.slice(value.trimEnd().length);
}

// In render, after cursor character:
{ghostSuffix && <Text color="gray">{ghostSuffix}{hasMultipleMatches && "↑"}</Text>}
```

No new component needed — derived from input value + recency map on every keystroke.

### 4.4 CompletionList Navigation (Changed from v0.3)

v0.3 uses Tab to cycle through the CompletionList. v0.4 changes to arrow-key navigation:

**New behavior:**
1. User types `/co` → ghost text shows most-recent match suffix (dimmed)
2. User presses **Tab** → accepts ghost hint, auto-completes the command, closes dropdown
3. User presses **Up/Down** → opens CompletionList dropdown if not already open, navigates through matches
4. As selection moves, ghost text updates to show the selected item's suffix
5. **Enter** on a selected item → fills the command and closes dropdown
6. **Escape** → closes dropdown, keeps current input text
7. Any character input → closes dropdown, continues typing

**Implementation change in InputBox.tsx:**
- Remove Tab cycling logic (`tabCycleRef` no longer needed for cycling)
- Tab now always accepts the current ghost hint (single action, no cycling)
- Up/Down arrows check if completions are showing before falling through to command history
- When CompletionList is open, Up/Down navigate within it; when closed, they do history as before

```typescript
// Up arrow priority:
if (completions.length > 0) {
  // Navigate CompletionList
  setCompletionIdx(Math.max(0, completionIdx - 1));
  buf.setValue(completions[completionIdx - 1].name + " ");
} else {
  // Command history (existing behavior)
  const entry = history.navigateUp(buf.value);
  if (entry != null) buf.setValue(entry);
}
```

## 5. Config Navigator Panel (Ctrl+N)

### 5.1 Component

New file: `src/tui/components/ConfigPanel.tsx`

A full-height overlay panel (replaces message area while open) with three tabs. While ConfigPanel is open, InputBox is **disabled** (focus state is `config-panel`) — all keyboard input is handled by the panel. InputBox re-enables when the panel closes via Escape.

| Tab | Content | Actions |
|-----|---------|---------|
| **Settings** | Browsable tree of SETTABLE_KEYS | Enter to edit value, Escape to cancel |
| **Models** | List of all provider/model entries | Enter to set as default, Space for details |
| **MCP** | Server list with status dots | Enter for tool list, `r` to reconnect |

### 5.2 Navigation

- **Ctrl+N** or **`/config`** (no subcommand) — Open ConfigPanel on Settings tab
- **`/model`** (no subcommand) — Open ConfigPanel directly on **Models** tab
- **`/mcp`** (no subcommand) — Open ConfigPanel directly on **MCP** tab

**Interface path for command→panel:** Bare commands return a `stateChange` with `configPanel` field (extending the existing `stateChange` contract that currently supports `planMode` and `showThinking`):

```typescript
// In commands/config.ts execute():
if (!subcommand) {
  return { output: "", stateChange: { configPanel: { open: true, tab: "settings" } } };
  // Empty output — panel open is the side effect. CommandResult.output is required by interface.
}

// In App.tsx command result handler:
if (stateChange?.configPanel) {
  dispatch({ type: "CONFIG_PANEL_OPEN", tab: stateChange.configPanel.tab });
}
```

This extends the existing `stateChange` pattern without breaking the current `CommandResult` interface — just adds an optional `configPanel` field.
- **Left/Right arrows** — Switch between tabs
- **Up/Down arrows** — Navigate items within current tab
- **Enter** — Select/edit focused item
- **Escape** — Close panel (or cancel in-progress edit)
- **Tab header** — Shows `[Settings]  Models   MCP` with active tab highlighted

## 6. Tool Enable/Disable

### 6.1 Config

`disabledTools: string[]` in `klayout.json` (parallels qdevbot's `instrmcp.json → disabledTools`). Tool names match exactly (e.g., `"klayout_geometry_add_rect"`).

### 6.2 Scope & Runtime Filtering

`disabledTools` applies **only to KLayout MCP and domain tools** — not to base tools (read, bash, edit, write) or custom tools (memory_save, memory_search). Base tools are always available; disabling them would break core agent functionality.

In `agent.ts` `assembleTools()`:

```typescript
// Collect all disabled tools: KLayout + generic MCP servers
const disabledSet = new Set(config.klayout.disabledTools);
for (const server of Object.values(config.mcp)) {
  if (server.disabledTools) {
    for (const t of server.disabledTools) disabledSet.add(t);
  }
}

// Base tools: never filtered
// KLayout MCP native tools + domain tools + generic MCP tools: filtered
const mcpEnabled = mcpTools.filter(t => !disabledSet.has(t.name));
const domainEnabled = domainTools.filter(t => !disabledSet.has(t.name));
// Custom tools: never filtered

const allTools = [...baseTools, ...mcpEnabled, ...domainEnabled, ...customTools];
```

### 6.3 Commands

Extend `/mcp` command:

- `/mcp disable <tool>` — Add to `disabledTools`, persist, log confirmation
- `/mcp enable <tool>` — Remove from `disabledTools`, persist, log confirmation
- `/mcp tools` — Show `[disabled]` tag next to disabled tools

### 6.4 TUI Integration

In ConfigPanel MCP tab, Space on a tool toggles enabled/disabled. Changes persist immediately via `saveKLayoutConfig()`.

### 6.5 Tool Annotations

Show emoji icons in tool listings and ConfigPanel:

| Icon | Field | Tools |
|------|-------|-------|
| 👀 | `readonly: true` | read, screenshot, get_layout_info, memory_search, capture, list_images |
| 🖊️ | `readwrite: true` | bash, edit, write, execute_script, add_rect, add_polygon, add_path, create_cell, add_instance |
| ⚡ | `backgroundable: true` | flakedetect, auto_route, save_layout |
| 🔒 | (from `disabledTools`) | Any disabled tool |

Annotation data defined in `src/tools/annotations.ts`:

```typescript
export const TOOL_ANNOTATIONS: Record<string, { readonly?: boolean; readwrite?: boolean; backgroundable?: boolean }> = {
  read: { readonly: true },
  bash: { readwrite: true },
  klayout_native_auto_route: { readwrite: true, backgroundable: true },
  // ...
};

export function getToolIcon(name: string, disabled: boolean): string {
  if (disabled) return "🔒";
  const ann = TOOL_ANNOTATIONS[name];
  let icon = "";
  if (ann?.backgroundable) icon += "⚡";
  if (ann?.readonly) icon += "👀";
  if (ann?.readwrite) icon += "🖊️";
  return icon || "🖊️";  // default to read-write
}
```

## 7. Input Focus Routing

### 7.1 The Problem

v0.3 InputBox owns Up/Down for command history. v0.4 adds three new consumers: CompletionList navigation, bar-selection mode, and ConfigPanel. A clear priority model is needed.

### 7.2 Focus States

The TUI has exactly one active focus state at a time:

| State | Owner | Up/Down | Tab | Enter | Escape |
|-------|-------|---------|-----|-------|--------|
| **input** (default) | InputBox | Command history | Accept ghost hint | Submit | Abort agent |
| **completion** | InputBox + CompletionList | Navigate completion items | Accept ghost hint | Fill selected command | Close dropdown → input |
| **bar-select** | App | Cycle through bars | — | Open selected bar | → input |
| **config-panel** | ConfigPanel | Navigate items within tab | — | Select/edit item | Close panel → input |
| **workspace-bar** | WorkspaceBar | Navigate files | — | Open file | Close → input |
| **background-bar** | BackgroundBar | Navigate tasks | — | — | Close → input |
| **subagent-summary** | SubagentPanel | Navigate entries | — | Inspect selected | Close → input |
| **subagent-inspect** | SubagentPanel | Scroll conversation | — | — | Back → subagent-summary |
| **subagent-inject** | SubagentPanel | — | — | Send message | Cancel → subagent-inspect |

*Note: `subagent-*` states are defined in Spec 2 and listed here for completeness of the global focus model.*

### 7.3 Transitions

```
input ──[Up/Down with `/` prefix + matches]──→ completion
input ──[Down with empty input]──────────────→ bar-select
input ──[Ctrl+N or /config or /model or /mcp]→ config-panel
input ──[Ctrl+W]─────────────────────────────→ workspace-bar
input ──[Ctrl+G]─────────────────────────────→ background-bar

completion ──[Escape or char input]──→ input
bar-select ──[Enter]─────────────────→ selected bar's state
bar-select ──[Escape]────────────────→ input
config-panel ──[Escape]──────────────→ input
workspace-bar ──[Escape]─────────────→ input
background-bar ──[Escape]────────────→ input

// Spec 2 subagent transitions:
input ──[Ctrl+S]─────────────────────→ subagent-summary
subagent-summary ──[Enter]───────────→ subagent-inspect
subagent-summary ──[Escape]──────────→ input
subagent-summary ──[i]───────────────→ subagent-inject
subagent-inspect ──[Escape]──────────→ subagent-summary
subagent-inspect ──[i]───────────────→ subagent-inject
subagent-inject ──[Enter]────────────→ subagent-inspect (message sent)
subagent-inject ──[Escape]───────────→ subagent-inspect (cancelled)
```

### 7.4 Up/Down Priority in InputBox

```typescript
if (key.upArrow || key.downArrow) {
  // Priority 1: CompletionList navigation (if dropdown is open)
  if (completions.length > 0) {
    navigateCompletions(key.upArrow ? -1 : 1);
    return;
  }

  // Priority 2: Bar navigation entry (Down + empty input + no completions)
  if (key.downArrow && buf.value === "") {
    dispatch({ type: "BAR_NAV_ENTER" });
    return;
  }

  // Priority 3: Command history (default)
  if (key.upArrow) {
    const entry = history.navigateUp(buf.value);
    if (entry != null) buf.setValue(entry);
  } else {
    const entry = history.navigateDown();
    if (entry != null) buf.setValue(entry);
  }
}
```

### 7.5 CompletionList Trigger

CompletionList opens when **Up or Down is pressed while typing a `/` prefix with 2+ matches** — not on every keystroke. This prevents the dropdown from interfering with normal history navigation:

```typescript
// On Up/Down while input starts with "/":
if (buf.value.startsWith("/") && completions.length === 0) {
  const matches = matchCommandsWithInfo(buf.value.trimEnd());
  if (matches.length > 1) {
    setCompletions(matches);
    setCompletionIdx(0);
    return;  // Don't fall through to history
  }
}
```

### 7.6 Bar Navigation

When InputBox is focused and user presses Down arrow (with empty input):
1. Enter **bar-select** focus state — a visual indicator highlights the first visible bar
2. Up/Down arrows cycle through visible bars (StatusBar, WorkspaceBar, BackgroundBar)
3. Enter opens/focuses the selected bar
4. Escape returns to input state

**Note**: ConfigPanel is NOT a bar — it's a full overlay opened via Ctrl+N or commands. Bar navigation only cycles through bottom status bars.

### 7.7 Bar Navigation State

```typescript
focusState: "input" | "completion" | "bar-select" | "config-panel" | "workspace-bar" | "background-bar"
  | "subagent-summary" | "subagent-inspect" | "subagent-inject";  // Added by Spec 2
barNavigationIndex: number;
```

**Migration from current App architecture**: Current `App.tsx` uses local `useState` booleans (`workspaceMode`, `backgroundMode`) and a global `useInput` handler for Escape. v0.4 replaces this with:

1. **`focusState` in reducer** — single source of truth for which component owns keyboard input
2. **App's `useInput`** checks `focusState` before handling any key. Only the focus owner processes keys:
   ```typescript
   // App.tsx global useInput:
   if (state.focusState !== "input" && key.escape) {
     // Delegate Escape to the focused component — don't handle here
     return;
   }
   ```
3. **Remove `workspaceMode`/`backgroundMode` local state** — replaced by `focusState === "workspace-bar"` / `focusState === "background-bar"`
4. Each panel component receives `isFocused` prop derived from `state.focusState` and only processes keys when focused

```typescript
// Example: WorkspaceBar only handles keys when it has focus
useInput((input, key) => {
  if (!isFocused) return;
  // handle Up/Down/Enter/Escape
}, { isActive: isFocused });
```

### 7.8 Visual

In bar-select mode, the focused bar gets a highlight border or inverse-video label. Other bars dim slightly.

## 8. Migration Summary

On first load after v0.4 update, the config loader performs these one-time migrations:

1. **KLayout MCP extraction**: `mcp.json → klayout_mcp` entry moves to `klayout.json`
2. **Bare model ID**: `"claude-sonnet-4-6"` → `"custom-anthropic/claude-sonnet-4-6"` in `model.json`
3. **History format**: `history.json` array → `{ entries: [...], recency: {} }` object

All migrations are idempotent (safe to run multiple times) and log a message on first run.

**Save conflict rules**: Save functions use read-merge-write. For arrays like `disabledTools`, the save function **replaces** the entire array (not append/remove). For objects, deep-merge with new values overwriting old. Missing keys are preserved (no deletion unless explicitly set to `null`).

## 10. Testing Strategy

### Testing Principles (from qdevbot patterns)

1. **Never trust agent output** — verify via file system reads, database queries, mock inspection
2. **State isolation** — each test gets its own `tmpDir` via `mkdtempSync()`, cleaned up in `afterEach`
3. **Mock inspection** — check what was *passed to* constructors/mocks, not what the agent *responded*
4. **Restriction enforcement** — verify restrictions at the tool wrapper level, not by trusting agent behavior
5. **Multi-layer verification** — file system + state machine + config round-trip in the same test
