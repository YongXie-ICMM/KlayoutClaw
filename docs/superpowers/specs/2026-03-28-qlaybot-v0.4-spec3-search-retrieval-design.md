## 1. Overview

Current memory search is FTS5 keyword-only (prefix matching with porter stemmer). This works for exact term recall but misses semantic matches — e.g., searching "fabrication steps" won't find a memory about "lithography process flow".

This spec adds two new retrieval stages and a **configurable search mode** that lets users choose the retrieval depth:

| Mode | Pipeline | Cost |
|------|----------|------|
| `fts5` | FTS5 only (current behavior) | Free, < 1ms |
| `fts5+rerank` | FTS5 → LLM Rerank | 1 Haiku call per search |
| `fts5+vector+rerank` | FTS5 + Vector → Union → LLM Rerank | Embedding API + 1 Haiku call |
| `vector+rerank` | Vector only → LLM Rerank | Embedding API + 1 Haiku call |

The mode is configurable via `settings.json`, `/config set search.mode`, or the ConfigPanel (Spec 1). Default: `fts5` (no additional API calls). Modes that include `vector` require an embedding API to be configured — if not set, those modes are unavailable and fall back to `fts5`.

## 2. Architecture

### 2.1 Current Pipeline (v0.3)

```
User Input → Sanitize → FTS5 Prefix Match → Top N → Format → Inject as <recalled-memories>
```

### 2.2 Proposed Pipeline (v0.4) — Mode-Dependent

```
search.mode determines which paths execute:

  fts5:              FTS5 ──────────────────────────────→ Top N → Inject
  fts5+rerank:       FTS5 ──────────────→ LLM Rerank ──→ Top N → Inject
  fts5+vector+rerank: FTS5 + Vector → Union → LLM Rerank → Top N → Inject
  vector+rerank:     Vector ─────────────→ LLM Rerank ──→ Top N → Inject
```

### 2.3 Design Principles

- **User-controlled depth** — the user picks the search mode based on their needs and available APIs
- **Graceful degradation** — if embedding API is not configured, modes with `vector` are unavailable and fall back to `fts5`
- **Budget-aware** — embedding + reranking cost tokens. The user explicitly opts in by choosing a mode.
- **Embed on reindex** — new/changed memory entries are embedded during `reindex()`, which is throttled by `minReindexMs`. Not on every save, and not lazily on first search — reindex is the single trigger.

## 3. Embedding Vector Search

### 3.1 Embedding Provider

Embedding requires a **separate API configuration** — it is not bundled with the main LLM provider. This is because:
- Not all LLM APIs offer embedding endpoints
- Embedding models are separate from chat models (different pricing, different endpoints)
- The user should explicitly opt in to the additional API cost

**Configuration**: The embedding API is set up via:
1. **SETUP wizard** (Spec 1) — optional step asking "Do you want to enable vector search? If so, provide an embedding API endpoint."
2. **ConfigPanel** (Spec 1) — Settings tab, under `embedding.*` keys
3. **`settings.json`** — manual editing

**If no embedding API is configured**, vector search is **disabled by default**. Search modes `fts5+vector+rerank` and `vector+rerank` are unavailable and fall back to `fts5`. The `/config set search.mode` command validates that the selected mode is possible with current config.

**Supported embedding APIs**: Any OpenAI-compatible `/embeddings` endpoint (OpenAI, Azure, local servers like Ollama). The `api` field specifies the endpoint format:
- `"openai-embeddings"` — `POST {baseUrl}/embeddings` with `{ model, input }` body. Covers OpenAI, Azure OpenAI, and compatible servers.

This mirrors the LLM provider `api` field (`"anthropic-messages"`, `"openai-chat"`) and allows future support for other embedding API formats without changing existing config.

### 3.2 Vector Storage

Extend the SQLite database with an embeddings table:

```sql
CREATE TABLE IF NOT EXISTS memory_embeddings (
  entry_hash TEXT PRIMARY KEY,      -- SHA-256 of (category + timestamp + content)
  category TEXT NOT NULL,
  timestamp TEXT NOT NULL,
  content TEXT NOT NULL,            -- Store content so embeddings are self-contained
  tags TEXT,                        -- Comma-separated tags
  embedding BLOB NOT NULL,          -- Float32Array as binary (1536 * 4 = 6144 bytes for text-embedding-3-small)
  created_at INTEGER NOT NULL       -- epoch ms
);
```

**Why `entry_hash` includes category + timestamp + content**: Prevents collisions when the same content appears in different categories or timestamps. Each unique memory entry gets its own embedding.

**Why store content/tags in the table**: Vector search results can be returned directly from the embeddings table without needing to resolve back to in-memory entries. This avoids the problem of embeddings becoming unresolvable when not all memory files are loaded (e.g., old log files).

### 3.3 Vector Index

For the expected memory volume (< 5000 entries), brute-force cosine similarity is fast enough (< 5ms for 5000 × 1536-dim vectors). No HNSW index needed.

```typescript
function cosineSimilarity(a: Float32Array, b: Float32Array): number {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

### 3.4 Embedding on Reindex

Extend `MemoryManager.reindex()`:

```typescript
async reindex(): Promise<void> {
  // Existing: parse markdown files, populate FTS5
  this.reindexFTS5();

  // New: embed entries that don't have embeddings yet
  await this.reindexEmbeddings();
}

private async reindexEmbeddings(): Promise<void> {
  const missing = this.entries.filter(e => !this.hasEmbedding(entryHash(e)));
  if (missing.length === 0) return;

  // Batch embed via single API call
  const texts = missing.map(e => `[${e.category}] ${e.tags.join(", ")}: ${e.content}`);
  const embeddings = await this.embedder.embedBatch(texts);

  const insert = this.db.prepare(
    "INSERT OR REPLACE INTO memory_embeddings (entry_hash, category, timestamp, content, tags, embedding, created_at) VALUES (?, ?, ?, ?, ?, ?, ?)"
  );
  for (let i = 0; i < missing.length; i++) {
    const e = missing[i];
    insert.run(entryHash(e), e.category, e.timestamp, e.content, e.tags.join(", "),
               Buffer.from(embeddings[i].buffer), Date.now());
  }
}
```

### 3.5 Vector Search

```typescript
async vectorSearch(query: string, limit: number): Promise<SearchResult[]> {
  const queryEmbedding = await this.embedder.embed(query);
  const threshold = this.config.embedding?.similarityThreshold ?? 0.3;

  // Read directly from embeddings table — self-contained, no in-memory lookup needed
  const rows = this.db.prepare(
    "SELECT entry_hash, category, timestamp, content, tags, embedding FROM memory_embeddings"
  ).all();

  const scored = rows.map(row => ({
    category: row.category,
    content: row.content,
    timestamp: row.timestamp,
    tags: row.tags ? row.tags.split(", ") : [],
    similarity: cosineSimilarity(queryEmbedding, new Float32Array(row.embedding.buffer)),
  }))
  .filter(s => s.similarity > threshold)
  .sort((a, b) => b.similarity - a.similarity)
  .slice(0, limit);

  return scored.map(s => ({
    category: s.category,
    content: s.content,
    timestamp: s.timestamp,
    tags: s.tags,
    rank: s.similarity,
  }));
}
```

## 4. LLM Reranking

### 4.1 When to Rerank

Reranking is triggered by the search mode — any mode ending in `+rerank` runs the reranker. Additionally:
- If results count is below `search.minRerank` (default: 4), skip reranking even in rerank modes (not enough to meaningfully reorder)
- If reranking fails, fall back to score-sorted results without reranking

### 4.2 Reranking Model

The reranker uses `claude-haiku-4-5-20251001` for speed and cost efficiency. Provider resolution:

1. Extract provider from `config.agent.defaultModel` (e.g., `custom-anthropic` from `custom-anthropic/claude-sonnet-4-6`)
2. Look up that provider in `config.models.providers`
3. Verify the provider's `api` field is `"anthropic-messages"` — Haiku is an Anthropic model and requires the Anthropic Messages API
4. If the provider is non-Anthropic (e.g., `api: "openai-chat"`), **find the first Anthropic provider** in `config.models.providers` instead
5. If no Anthropic provider exists at all, reranking is **unavailable** — modes with `+rerank` fall back to their non-rerank equivalent (`fts5+rerank` → `fts5`, `fts5+vector+rerank` → `fts5`, `vector+rerank` → disabled)

This means reranking works automatically when the user has any Anthropic-compatible provider configured (which is the default setup). No additional config needed.

### 4.3 Reranking Prompt

```typescript
async function rerankResults(
  results: SearchResult[],
  query: string,
  config: QlayBotConfig
): Promise<SearchResult[]> {
  // Find an Anthropic provider for Haiku reranking
  const anthropicProvider = findAnthropicProvider(config);
  if (!anthropicProvider) throw new Error("No Anthropic provider available for reranking");
  const modelId = "claude-haiku-4-5-20251001";

  const response = await client.messages.create({
    model: modelId,
    max_tokens: config.search.rerankMaxTokens ?? 256,
    system: "You are a relevance scorer. Given a query and a list of memory snippets, score each snippet 0-100 for relevance. Return ONLY a JSON array of scores in the same order: [score1, score2, ...]",
    messages: [{
      role: "user",
      content: `Query: "${query}"\n\nSnippets:\n${results.map((r, i) =>
        `${i + 1}. [${r.category}] ${r.content.slice(0, 200)}`
      ).join("\n")}`
    }],
  });

  const scores = JSON.parse(extractText(response));
  return results
    .map((r, i) => ({ ...r, rank: scores[i] / 100 }))
    .filter(r => r.rank >= (config.search.rerankMinScore ?? 0.3))
    .sort((a, b) => b.rank - a.rank);
}
```

### 4.4 Error Handling

If reranking fails (API error, parse error, timeout, no Anthropic provider):
- Log warning
- Fall back to the retrieval results (FTS5, vector, or both — depending on mode) sorted by normalized score, without reranking
- Never block auto-recall on a rerank failure

### 4.5 Caching

Cache rerank results for identical queries within the same reindex cycle:
- Key: `SHA-256(query + sorted entry_hashes of results)` — `entry_hash` is the same hash used in the embeddings table, computed from `category + timestamp + content`
- Expires on reindex (clear cache when `reindex()` runs)
- Avoids redundant LLM calls for repeated queries

## 5. Hybrid Search Integration

### 5.1 Updated search() Method — Mode-Driven

```typescript
type SearchMode = "fts5" | "fts5+rerank" | "fts5+vector+rerank" | "vector+rerank";

async search(query: string, limit = 5): Promise<SearchResult[]> {
  const mode = this.resolveMode();  // Validates mode against available APIs

  // Step 1: Retrieve candidates based on mode
  let candidates: SearchResult[] = [];

  if (mode === "fts5" || mode === "fts5+rerank" || mode === "fts5+vector+rerank") {
    candidates.push(...this.ftsSearch(query, limit * 2));
  }

  if (mode === "fts5+vector+rerank" || mode === "vector+rerank") {
    candidates.push(...await this.vectorSearch(query, limit * 2));
  }

  // Step 2: Deduplicate (only needed when both paths ran)
  if (mode === "fts5+vector+rerank") {
    candidates = deduplicateResults(candidates);
  }

  // Step 3: Rerank if mode includes it and enough results
  if (mode.includes("+rerank") && candidates.length >= (this.config.search?.minRerank ?? 4)) {
    const reranked = await this.rerankResults(candidates, query);
    return reranked.slice(0, limit);
  }

  // No rerank: sort by normalized score
  return candidates.sort((a, b) => b.rank - a.rank).slice(0, limit);
}

private resolveMode(): SearchMode {
  // Mode is validated at config-set time (see §7.3):
  // - Vector modes rejected if no embedding API configured
  // - Rerank modes rejected if no Anthropic provider available
  // So at runtime, the configured mode is always valid.
  // Only fall back if config was manually edited to an invalid state.
  const configured = this.config.search?.mode ?? "fts5";
  if ((configured === "fts5+vector+rerank" || configured === "vector+rerank") && !this.embedder) {
    return "fts5";  // Safety fallback for manually edited config
  }
  if (configured.includes("+rerank") && !this.rerankAvailable) {
    // Can't strip "+rerank" and get a valid mode — always fall back to "fts5"
    // ("fts5+vector" and "vector" are not valid SearchMode values)
    return "fts5";
  }
  return configured;
}
```

### 5.2 Deduplication

```typescript
function deduplicateResults(results: SearchResult[]): SearchResult[] {
  const seen = new Map<string, SearchResult>();
  for (const r of results) {
    const hash = contentHash(r);
    const existing = seen.get(hash);
    if (!existing || r.rank > existing.rank) {
      seen.set(hash, r);  // Keep highest-ranked duplicate
    }
  }
  return Array.from(seen.values());
}
```

### 5.3 Score Normalization

FTS5 and vector results must be on the same scale (0-1, higher = better) before merging or comparing.

**FTS5**: Current qlaybot code already flips FTS5 ranks to positive (higher = better) via `rank * -1` in the SQL query. Normalize to 0-1 by dividing by the max rank in the result set:

```typescript
function normalizeFTSRanks(results: SearchResult[]): SearchResult[] {
  if (results.length === 0) return results;
  const maxRank = Math.max(...results.map(r => r.rank));
  if (maxRank === 0) return results;
  return results.map(r => ({ ...r, rank: r.rank / maxRank }));
}
```

**Vector similarity**: Already 0-1 (cosine similarity), no normalization needed.

### 6.1 Interface

### 6.2 API Embedder

The only supported embedder type. Requires a configured embedding API endpoint:

```typescript
export class APIEmbedder implements Embedder {
  readonly dimensions: number;

  constructor(
    private baseUrl: string,
    private apiKey: string,
    private model: string,
    dims: number
  ) {
    this.dimensions = dims;
  }

  async embed(text: string): Promise<Float32Array> {
    // POST to baseUrl/embeddings with OpenAI-compatible format:
    // { model, input: text }
    // Response: { data: [{ embedding: number[] }] }
    const res = await fetch(`${this.baseUrl}/embeddings`, {
      method: "POST",
      headers: { "Authorization": `Bearer ${this.apiKey}`, "Content-Type": "application/json" },
      body: JSON.stringify({ model: this.model, input: text }),
    });
    const json = await res.json();
    return new Float32Array(json.data[0].embedding);
  }

  async embedBatch(texts: string[]): Promise<Float32Array[]> {
    // OpenAI embeddings API supports batch input natively
    const res = await fetch(`${this.baseUrl}/embeddings`, {
      method: "POST",
      headers: { "Authorization": `Bearer ${this.apiKey}`, "Content-Type": "application/json" },
      body: JSON.stringify({ model: this.model, input: texts }),
    });
    const json = await res.json();
    return json.data.map((d: { embedding: number[] }) => new Float32Array(d.embedding));
  }
}
```

### 6.3 Factory

```typescript
export function createEmbedder(config: QlayBotConfig): Embedder | null {
  const emb = config.embedding;
  // Only create embedder if API is fully configured
  if (!emb?.baseUrl || !emb?.apiKey || !emb?.model) return null;

  return new APIEmbedder(emb.baseUrl, emb.apiKey, emb.model, emb.dimensions ?? 1536);
}
```

Returns `null` if embedding API is not configured → vector search modes are unavailable → `resolveMode()` falls back to `fts5`.

## 8. Database Migration

### 8.1 From In-Memory to Disk

Current qlaybot uses `:memory:` SQLite. For embedding persistence, migrate to disk-based:

**Path**: `~/.qlaybot/memory/index.sqlite`

This avoids re-embedding all entries on every startup (which would be slow for local model init + batch embed).

FTS5 table remains the same. Embeddings table is new.

### 8.2 Migration Logic

In `MemoryManager` constructor:
1. Check if `index.sqlite` exists
2. If not: create database with both FTS5 + embeddings tables
3. If yes: check if `memory_embeddings` table exists, create if missing
4. Existing `:memory:` behavior becomes fallback when disk path unavailable

## 9. Performance Budget

### 9.1 Latency Targets

| Stage | Target | Notes |
|-------|--------|-------|
| FTS5 search | < 1ms | Already achieved |
| API embedding (query) | < 200ms | Network round-trip to embedding API |
| Vector search (brute force, 5000 entries) | < 5ms | 5000 × 1536 cosine similarity |
| LLM rerank (Haiku) | < 500ms | Network-dependent |
| **Total `fts5` mode** | < 1ms | No change from v0.3 |
| **Total `fts5+rerank` mode** | < 500ms | 1 Haiku call |
| **Total `fts5+vector+rerank` mode** | < 700ms | Embedding API + Haiku call |

### 9.2 Mitigations

- **Rerank caching**: Cache rerank results per query within reindex cycle
- **Embedding batch**: On reindex, batch all new entries into a single API call (cheaper + faster than per-entry calls)
- **Throttled reindex**: `minReindexMs` (default 5000ms) prevents excessive embedding API calls
- **`fts5` mode is zero-cost**: Users who don't need semantic search stay on the fast path with no API overhead

### 9.3 Memory Budget

- Embedding storage: 5000 entries × 6144 bytes (1536 × 4) = ~30MB on disk
- In-memory: embeddings loaded lazily on search, not all at once

## 11. Testing Strategy

### Testing Principles (from qdevbot patterns)

1. **Database-level verification** — query SQLite tables directly to verify FTS5 and embedding storage, not through the search API
2. **Mock HTTP for embedding API** — mock `fetch` to control embedding responses without real API calls
3. **State isolation** — each test gets its own `tmpDir` with fresh SQLite database
4. **Multi-layer verification** — database content + search results + auto-recall injection in the same test
5. **Mode-driven testing** — test each of the 4 search modes independently with appropriate mocks

### Unit Tests (~40 new tests)

**Embedder factory** (config-driven creation):

- Streaming rerank (progressive result refinement)
- Custom rerank model selection (always Haiku for cost/speed)
