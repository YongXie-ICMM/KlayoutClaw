## 1. Overview

Wire up the subagent delegation system that v0.3 stubbed (`PromptMode.Sub` exists but is unused). The user wants subagents to run autonomously but with full TUI visibility and the ability to interrupt and inject clarifications mid-run.

Four feature areas:
1. **Subagent runner** — role-based delegation with tool scoping, budget enforcement, transcript logging
2. **Delegate tool** — parent agent's interface to spawn subagents
3. **TUI progress panel** — real-time subagent visibility (SubagentPanel)
4. **Interrupt/inject** — user can pause a subagent and send a message

## 2. Role System

### 2.1 Fully Dynamic Roles

Roles are **entirely config-driven** — there are no hardcoded role names in code. The runner accepts any string as a role name and resolves its `RoleConfig` from `settings.json`. The codebase ships a **template** `settings.json` with suggested roles, but users can add, modify, or remove any role.

### 2.2 RoleConfig Interface

```typescript
export type SubagentRole = string;  // No enum — any name is valid

export interface RoleConfig {
  label: string;                   // Human-readable display name
  promptFile: string;              // Path relative to workspace/ (e.g., "subagent/scout.md")
  workspaceFiles: string[];        // Workspace docs to inject in system prompt
  baseTools: string[];             // "read", "bash", "write", "edit"
  customTools: string[];           // "memory_search", "submit_result", domain tools
  mcpAccess: "shared-readonly" | "full" | "none";
  maxTurns: number;
  maxTokens: number;
  model?: string;                  // Override default model
  thinkingLevel?: string;          // Override thinking level
}
```

### 2.3 Shipped Default Roles (Template)

The `settings.json` template ships with four suggested roles. Users can modify or replace these:

| Role | Purpose | Base Tools | MCP Access | Max Turns | Max Tokens |
|------|---------|-----------|------------|-----------|------------|
| **scout** | Read-only exploration: layout inspection, layer queries, parameter discovery | read | shared-readonly | 100 | 200k |
| **designer** | Geometry creation: draw shapes, place instances, modify layout | read, bash, write | full | 100 | 200k |
| **analyst** | Analysis: capture screenshots, evaluate GDS files, compare designs | read, bash, write, edit | shared-readonly | 100 | 200k |
| **planner** | Planning: design review, fabrication constraint analysis, workflow design | read | shared-readonly | 100 | 200k |

**Example custom role** (user-defined in `settings.json`):
```json
{
  "subagent": {
    "roles": {
      "fab-checker": {
        "label": "Fabrication Rule Checker",
        "promptFile": "subagent/fab-checker.md",
        "workspaceFiles": ["RULES.md"],
        "baseTools": ["read"],
        "customTools": ["memory_search", "submit_result"],
        "mcpAccess": "shared-readonly",
        "maxTurns": 50,
        "maxTokens": 100000
      }
    }
  }
}
```

### 2.4 Tool Scoping

Tool access is determined entirely by the role's `baseTools`, `customTools`, and `mcpAccess` fields — no hardcoded per-role logic. The runner reads these fields and assembles the tool set dynamically.

**MCP access modes:**
- `"shared-readonly"` — uses parent's MCP connection, blocks write operations (`execute_script`, `auto_route`, geometry tools). Allows `get_layout_info`, `screenshot`, display tools, visual tools.
- `"full"` — full MCP access including write operations
- `"none"` — no MCP tools at all

**Read-only MCP proxy**: Wraps KLayout MCP calls to block write tools. Uses the tool annotations from Spec 1 (`readonly: true` passes, `readwrite: true` blocked).

Tools disabled in `klayout.json → disabledTools` (and generic MCP `disabledTools`) are unavailable to all roles regardless of their config.

**`memory_search` integration with Spec 3**: Subagents receive access to the **parent's `MemoryManager` instance** for `memory_search`. This means subagent searches use the same hybrid retrieval pipeline (FTS5, vector, rerank) as the parent agent, governed by the same `search.mode` config. The subagent does not get a separate memory manager or search config.

### 2.5 Role Resolution

New file: `agent/src/subagent/role-resolver.ts`

```typescript
export function resolveRole(roleName: string, config: QlayBotConfig): RoleConfig | null {
  return config.subagent?.roles?.[roleName] ?? null;
}

export function listRoles(config: QlayBotConfig): string[] {

```

If the parent agent calls `delegate` with an unknown role name, the delegate tool returns an error listing available roles.

## 3. Subagent Runner

### 3.1 SubagentRunner Class

New file: `agent/src/subagent/runner.ts`

```typescript
export class SubagentRunner {
  constructor(deps: SubagentRunnerDeps);
  async run(options: SubagentRunOptions): Promise<SubagentResult>;
}
```

### 3.2 Execution Pipeline

14-step execution pipeline, adapted from qdevbot for qlaybot:

1. **Resolve role config** — look up `roleName` in `config.subagent.roles`. If not found, return error. No code defaults — the role must be fully defined in config.
2. **Result callback** — first-wins capture from `submit_result` tool call
3. **Create tools** — `createSubagentTools(roleConfig, deps)` returns scoped tool set
4. **Transcript logger** — records all interactions to `~/.qlaybot/subagent-logs/`
5. **Build system prompt** — role prompt + workspace files + tool listing + budget notice
6. **Create ephemeral session** — `SessionManager.inMemory`, no auto-compaction
7. **Resolve model** — from roleConfig.model or config.agent.defaultModel
8. **Construct Agent + AgentSession** — with transformContext (pruner only)
9. **Budget enforcement subscription** — turn ceiling + token budget + streaming check
10. **Send task message** — blocks until completion or budget exceeded
11. **Post-prompt handling** — synthesize partial result if budget exceeded
12. **Cleanup** — dispose session
13. **Save transcript** — write markdown to disk
14. **Return SubagentResult**

### 3.3 SubagentResult

```typescript
export interface SubagentResult {
  role: SubagentRole;
  task: string;
  status: "completed" | "partial" | "error";
  findings: string[];
  warnings: string[];
  dataPaths: string[];
  tokenUsage: { inputTokens: number; outputTokens: number; totalTokens: number; turns: number };
  transcriptPath: string;
  errorMessage?: string;
}
```

### 3.4 Budget Enforcement

Three checkpoints (same as qdevbot):
1. **turn_start** — abort if turns >= maxTurns
2. **turn_end** — abort if tokens >= maxTokens
3. **message_update** — abort during streaming if tokens >= maxTokens

When budget exceeded: `session.abort()`, set `budgetExceeded` flag, synthesize partial result.

### 3.5 Transcript Logging

New file: `agent/src/subagent/transcript.ts`

- Storage: `{config.subagent.logDir}/{ISO-TIMESTAMP}-{role}.md` (default: `~/.qlaybot/subagent-logs/`)
- Log rotation: keep last 100 files (configurable)
- Entry types: user, assistant, tool_call, tool_result
- Tool results stored in FULL in transcript (not truncated) — transcripts are the permanent record. TUI inspect window truncates for display only; Ctrl+T expands.

## 4. Delegate Tool

### 4.1 Tool Definition

New file: `agent/src/tools/delegate.ts`

```typescript
export function createDelegateTool(runner: SubagentRunner): ToolDefinition;
```

- **Name**: `delegate`
- **Parameters**: `{ role: string, task: string, context?: string }`
- **Returns**: Formatted SubagentResult as JSON
- **Validation**: If `role` is not found in `config.subagent.roles`, returns error with list of available roles

**Not wrapped for background execution** — subagents have their own budget enforcement. Auto-backgrounding would lose results.

### 4.2 Integration in agent.ts

In `createDesignSession()`:
1. Resolve subagent config from `settings.json`
2. If `subagent.enabled`, create `SubagentRunner` with deps
3. Add `createDelegateTool(runner)` to custom tools. Add `"delegate"` to the plan mode sandbox `ALLOWED_TOOLS` set (in `agent/src/planning/sandbox.ts`) so delegation works even when the parent is in plan mode.
4. Pass `hasDelegate: true` to system prompt builder (adds delegation instructions)
5. Expose `subagentRunner` on `QlayBotSession` for TUI event wiring

### 4.3 System Prompt Section

When `hasDelegate` is true, add to system prompt. The role list is **generated dynamically** from `config.subagent.roles`:

```
## Delegation

You can delegate specialized tasks to subagents using the `delegate` tool.

Available roles:
- **scout**: Read-only layout exploration and parameter discovery
- **designer**: Geometry creation and layout modification
- ...

Each subagent runs in isolation with role-specific tools and returns structured findings.
Use delegation for tasks that benefit from focused execution.
```

Built by iterating `config.subagent.roles` and emitting each role's name + label. If users add custom roles, they automatically appear in the prompt.

### 4.4 `submit_result` Tool Contract

Each subagent gets a `submit_result` tool that captures structured findings. Defined in `agent/src/subagent/tool-factory.ts`:

```typescript
// Tool name: "submit_result"
// Parameters:
{
  status: "completed" | "partial" | "error";   // Required
  findings: string[];                          // Key findings/observations
  warnings: string[];                          // Safety concerns or unexpected values
  data_paths: string[];                        // File paths to created/referenced data
  error_message?: string;                      // Only when status is "error"
}
// Returns: { acknowledged: true }
```

The runner registers a **first-wins callback** — the first `submit_result` call captures the payload, subsequent calls are ignored. If the subagent never calls `submit_result` (budget exceeded or error), the runner synthesizes a partial result from available context.

The subagent's system prompt includes instructions to call `submit_result` exactly once before finishing (see §3.2 step 5).

### 4.5 Nested Delegation Prevention

The `delegate` tool is **never included** in a subagent's tool set. The tool factory explicitly excludes it regardless of the role's `customTools` config. This prevents subagent-to-subagent delegation (infinite recursion). If a user adds `"delegate"` to a role's `customTools`, it is silently filtered out and logged as a warning.

## 5. TUI Progress Panel (SubagentPanel)

### 5.1 Component

New file: `agent/src/tui/components/SubagentPanel.tsx`

A two-level panel for subagent visibility. Opens via **Ctrl+S**, mutually exclusive with other panels.

**Escape key routing**: When SubagentPanel has focus (either summary or inspect level), Escape is handled by the panel (close/back). The panel takes focus away from InputBox, so the existing App-level Escape→abort handler does **not** fire. This follows the same focus routing model as Spec 1 section 7 — only the active focus owner receives Escape. When the panel closes, focus returns to InputBox, and Escape reverts to its normal abort behavior.

### 5.2 Display (Collapsed — StatusBar Badge)

In StatusBar, when `activeSubagents > 0`:
```
... | 2 sub | ...
```
Magenta text, shows count of active subagents. Derived from `state.subagents.filter(s => s.status === "running").length` — no separate counter field needed. Ctrl+S expands to summary bar.

### 5.3 Level 1: Summary Bar

A compact list of all subagents (active + recent). Navigate with **Up/Down**, **Enter** to inspect a specific subagent.


**Inspect window contents** (scrollable, auto-follows latest):
- **🤔 Thinking** — subagent's thinking/reasoning text (truncated, last ~5 lines)
- **💬 Text** — subagent's assistant message text
- **🔧 Tool call** — tool name + key arguments, then result summary (truncated in collapsed mode)
- **📨 Injected** — user-injected messages (section 6) shown in cyan

**Ctrl+T** toggles expanded/collapsed view in inspect window (same shortcut as main TUI's tool detail + thinking expansion). When expanded: full thinking text and full tool results are shown. When collapsed: thinking shows last ~5 lines, tool results show summary only. **Transcript files always store full content** (not truncated).

- **Left/Right arrows** — switch to previous/next subagent (wraps around). The header updates to show the new subagent's role/task/time.
- **Up/Down arrows** — scroll through the conversation history
- **`i`** — inject a message (section 6)
- **`k`** — kill the subagent
- **Escape** — back to summary bar (level 1)

### 5.6 Event Bridge

The subagent's session events don't naturally surface to the parent TUI. SubagentRunner emits granular events via an EventEmitter:

```typescript
runner.on("thinking", (subagentId, text) => { ... });
runner.on("text", (subagentId, text) => { ... });
runner.on("tool_start", (subagentId, toolName, args) => { ... });
runner.on("tool_end", (subagentId, toolName, result) => { ... });
runner.on("turn", (subagentId, turnNumber, tokens) => { ... });
```

The App subscribes to runner events and dispatches the corresponding `SUBAGENT_*` actions. This gives real-time visibility into each subagent's conversation — thinking, text, tool calls, and results — streamed live into the inspect window.

### 5.7 ID Mapping: toolCallId ↔ subagentId

The delegate tool runs as a parent tool call (with a `toolCallId`), but the runner generates its own `subagentId` for internal tracking and event routing. These must be correlated:

1. **App.tsx detects `delegate` in `tool_execution_start`** → dispatches `SUBAGENT_PLACEHOLDER` with `toolCallId`, role, task (from args). Entry is created with `id: toolCallId` temporarily.
2. **Runner emits `"started"` event** with `{ subagentId, toolCallId }` immediately after session creation → App dispatches `SUBAGENT_START` which updates the placeholder entry's `id` from `toolCallId` to `subagentId`.
3. **All subsequent runner events** use `subagentId` → reducer matches by `id`.
4. **On `tool_execution_end`** for delegate → App matches by `toolCallId` (stored as secondary key on the entry) to dispatch `SUBAGENT_END`.

```typescript
// Runner emits on session creation:
this.emit("started", { subagentId, toolCallId, role, task });

// SubagentTUIEntry stores both:
interface SubagentTUIEntry {
  id: string;              // subagentId (canonical, used by all runner events)
  toolCallId: string;      // delegate toolCallId (used to correlate tool_execution_end)
  // ...
}
```

### 5.8 Event Bridge

**Implementation**: In `SubagentRunner.run()`, subscribe to the ephemeral session's events using the actual event model from `agent/src/events.ts`:

- `message_update` → extract thinking/text deltas, re-emit as `runner.emit("thinking", id, text)` or `runner.emit("text", id, text)` based on content type
- `tool_execution_start` → re-emit as `runner.emit("tool_start", id, toolName, args)`
- `tool_execution_end` → re-emit as `runner.emit("tool_end", id, toolName, result)`

The runner translates the session's raw event model into the granular events the TUI reducer expects. Each event is prefixed with the subagent ID so the App can dispatch to the correct `SubagentTUIEntry`.

## 6. Interrupt/Inject

### 6.1 Behavior

When a subagent is running and the user presses `i` on the focused entry (in summary bar or inspect window):

1. SubagentRunner **pauses** the targeted session (waits for current tool to finish, then holds before next prompt)
2. Focus state transitions to `"subagent-inject"` — a new focus state in the Spec 1 focus routing model
3. TUI renders an inline input field at the bottom of SubagentPanel: `inject [role]> _` with cursor editing (reuses `useInputBuffer` hook)
4. InputBox is disabled while inject input has focus
5. User types a message and presses **Enter** → message is injected, focus returns to panel, subagent resumes
6. **Escape** → cancels inject (resumes subagent without injecting), focus returns to panel

**Inject state in reducer:**
```typescript
subagentInjectMode: boolean;
subagentInjectTarget: string | null;  // subagent ID being injected into
subagentInjectValue: string;          // current input text
```

### 6.2 Kill

Press `k` on a focused running entry:
1. SubagentRunner calls `session.abort()`
2. Synthesizes partial result
3. Entry updates to `status: "partial"` with message "Killed by user"

### 6.3 Implementation

SubagentRunner manages **multiple concurrent subagent sessions**. Each `run()` call creates an independent session tracked by a unique subagent ID. Control methods take a subagent ID to target the correct session:

```typescript
export class SubagentRunner extends EventEmitter {
  // Active sessions indexed by subagent ID
  private sessions: Map<string, SubagentSession> = new Map();

  async run(options: SubagentRunOptions): Promise<SubagentResult>;

  // Per-subagent control
  async pause(subagentId: string): Promise<void>;
  async resume(subagentId: string): Promise<void>;
  async inject(subagentId: string, message: string): Promise<void>;
  async kill(subagentId: string): Promise<void>;

  // Query
  getActive(): string[];  // List active subagent IDs
}

interface SubagentSession {
  id: string;
  role: string;
  session: AgentSession;
  paused: boolean;
  resumeResolve: (() => void) | null;
}
```

The pause mechanism works by inserting a gate in each session's budget enforcement `turn_start` handler:
```typescript
if (subagentSession.paused) {
  await new Promise<void>(resolve => { subagentSession.resumeResolve = resolve; });
}
```

`inject(id, message)` appends a user message to the targeted session, then calls `resume(id)`.

`run()` generates a unique ID (e.g., `${role}-${Date.now()}`), registers the session in `this.sessions`, and removes it on completion/error/kill.

### 6.4 Limitations

- Injection happens between turns (not mid-tool-execution)
- The subagent sees the injected message as additional context, not as a new task
- **Kill behavior**: `session.abort()` is called immediately, which sets a flag that prevents the next prompt from firing. If a tool is currently executing, the tool runs to completion (no forceful mid-tool termination), then the session stops. The result is synthesized as `status: "partial"` with the message "Killed by user".

**Validation**: On config load, validate each role has all required `RoleConfig` fields. Missing fields → log warning and skip the role (don't crash). The `delegate` tool only offers roles that passed validation.

### 7.3 Workspace Prompt Files

Create template prompt files for the shipped default roles. Custom roles reference their own prompt files via `promptFile` in config — the runner loads whatever path is specified.

```
workspace/subagent/
├── scout.md      — Read-only exploration instructions
├── designer.md   — Geometry creation guidelines + layer rules
├── analyst.md    — Analysis workflow + evaluation criteria
└── planner.md    — Planning methodology + constraint awareness
```

Each file incorporates domain knowledge from existing `SOUL.md`, `RULES.md`, `WORKFLOW.md`. Users creating custom roles write their own prompt files and reference them in `settings.json`.

## 9. Testing Strategy

### Testing Principles (from qdevbot patterns)

1. **Mock the Agent SDK** — `vi.mock("@mariozechner/pi-agent-core")` + `vi.mock("@mariozechner/pi-coding-agent")` to inspect what was passed to Agent/AgentSession constructors
2. **Verify tool availability per role** — explicitly test what each role can/cannot access at the tool-factory level
3. **Simulate agent behavior via mockPrompt** — `mockPrompt.mockImplementation()` to simulate subagent calling `submit_result`
4. **File system verification** — read transcript files directly, verify content structure
5. **State isolation** — tmpDir per test for logDir, workspace, memory
