## 0. Divergences from qdevbot (explicit)

The spec previously claimed byte-for-byte parity; that was imprecise. The following are *intentional* differences qlaybot must preserve:

| # | Divergence | Reason |
|---|-----------|--------|
| D1 | `PlanManager.enterPlanMode` catches FS errors internally and returns a structured `{status:"error"}` via the tool wrapper instead of letting the exception propagate out of the manager. | qdevbot throws from the manager; qlaybot's RPC transport treats unhandled exceptions as session-fatal, so we must surface failure as a tool-result instead. |
| D2 | qlaybot adds `isReadOnlyTool` + `wrapMCPToolForPlanMode` as a *separate* module (not baked into a monolithic `instrmcp` proxy). | qdevbot routes every tool call through one `instrmcp` proxy; qlaybot has a general `MCPManager` with many separately-registered tools. |
| D3 | Plan approval menu opens **only** on the `/plan` (no-args) slash-exit path. If the model calls `exit_plan_mode` as a tool, the TUI does NOT open the menu — the tool result carries `status:"plan_approved"` and control returns to the agent loop. | Exact qdevbot behavior (`App.tsx:480-529` shows menu only from the slash path; the tool result does not trigger it). Keeping this parity is explicit. |
| D4 | `writePlanContent` does NOT auto-recreate a deleted plan file; callers must use `enterPlanMode` to (re)create. | Matches qdevbot; the earlier test "auto-recreate after delete" was wrong and is removed. |
| D5 | Annotation shape: qlaybot keeps its existing `{readonly, readwrite, backgroundable}` triple and adds an accessor `getReadOnlyForPlanMode(toolName)` that derives the boolean from the existing fields — no MCP-standard hint migration in 0.4.3. | Avoids a breaking change to `ConfigPanel`, `subagent/tool-factory`, `types/v04-contracts`, and icon logic. Deny-by-default preserved: unknown tool → false. |
| D6 | Plan mode system-prompt injection lives entirely in the `enter_plan_mode` tool result text. There is no equivalent to qlaybot 0.4.2's `PlanManager.getSystemPromptInjection()` (which injected via `transformContext`). | Tool-result-based injection is the qdevbot pattern and avoids the context-bloat risk of keeping the injection active across every turn. |
| D7 | Subagents do NOT inherit plan mode (identical to qdevbot) — but the spec now explicitly documents this as a **trust tradeoff** and gates the `delegate` tool behind an explicit opt-in when the parent is in plan mode. | Pure qdevbot parity leaves a subagent-shaped hole through the sandbox; we narrow it. |

## Summary

Version 0.4.3 adds one major feature and three minor features to qlaybot:

| Feature | Type | One-line summary |
|---------|------|------------------|
| **Plan Mode** | Major | Tool-based + slash-command plan mode with disk-persisted plan files and 4-option approval menu. Byte-for-byte port of qdevbot's implementation, adapted to the KLayout domain. |
| TUI image render | Minor | Decode `type: "image"` tool-result content to iTerm2 OSC 1337 inline escape, with terminal detection + save-to-file fallback. |
| Transcript truncate | Minor | Auto-truncate tool-result entries > 2000 chars in `~/.qlaybot/history/.../transcript.jsonl` and the per-tool JSON files, using 1000-head + 1000-tail with an `... (truncated N chars) ...` marker. |
| `--verbose` flag | Minor | Disables both TUI and disk truncation, prints the assembled system prompt on startup, emits per-turn timing + token stats, and writes a full-fidelity project-local transcript copy to `./qlaybot-transcripts/{sessionId}-{timestamp}.jsonl`. |

Integration approach: **refactor + unified truncation** (approach B from brainstorm). Replace qlaybot's existing skeletal `src/planning/index.ts` with a qdevbot-aligned `PlanManager`. One shared `src/truncation.ts` module powers both display and disk truncation; `--verbose` toggles it off in both places.

## 1. Plan Mode (Major)

### 1.1 Scope

qlaybot v0.4.2 already has a scaffolding for plan mode (`src/planning/index.ts`, `src/planning/sandbox.ts`, `src/commands/plan.ts`) — in-memory, slash-command-only, no plan-file persistence, no approval flow. 0.4.3 replaces this with a full qdevbot-parity implementation: dual entry paths (slash command + tools), disk persistence, sandboxed tool wrapping, and a TUI approval menu.

### 1.2 PlanManager (`src/planning/index.ts`, rewritten)

Port from qdevbot `src/planning/manager.ts` (217 lines) — verbatim port of:
- Private state fields: `_inPlanMode: boolean`, `_currentPlan: Plan | null`, `_plansDir: string`, `_listeners: PlanEventListener[]`.
- Public getters: `inPlanMode`, `currentPlan`, `plansDir`.
- Methods: `enterPlanMode(task: string, title?: string): Plan`, `exitPlanMode(approved?: boolean = true): Plan | null`, `reenterPlanMode(): Plan | null`, `updatePlanTasks(tasks: PlanTask[]): void`, `readPlanFile(): string | null`, `writePlanContent(content: string): void`, `subscribe(listener: PlanEventListener): () => void`.
- Private helpers: `_emit(event)`, `_deriveTitle(task)`, `_buildPlanFileContent(plan)`, `_writePlanFile(plan)`.
- Constructor: `new PlanManager(workspaceDir: string)` — sets `_plansDir = join(workspaceDir, "plans")`.

**Plan ID format**: `plan-${Date.now()}`. If `${plansDir}/plan-${Date.now()}.md` already exists (Date.now collision under rapid repeated entry), append a monotonic counter: `plan-${Date.now()}-${n}.md`, incrementing `n` from 1 until a non-existing path is found (max 10 attempts before throwing).
**Plan file path**: `${plansDir}/${planId}.md`.
**Error handling** (divergence D1): `enterPlanMode` wraps `mkdirSync` + `writeFileSync` in try/catch; on failure (e.g., read-only workspace, disk full, EACCES), the method returns `null` and emits no event. The `enter_plan_mode` tool wrapper translates `null` into `{status: "error", message: "Failed to create plan file: ${err.message}"}` without mutating `_inPlanMode` or `_currentPlan`. Exceptions are logged but not propagated to the agent loop.

**Plan file template** (emitted by `_buildPlanFileContent`, exact):

```
# {title}

## Task
{task}

## Plan

<!-- The agent will fill in the plan during plan mode -->

## Tasks

<!-- Checklist of implementation tasks -->
```

**Status marker** prepended on `exitPlanMode`:
- `approved` → `> Status: **approved**\n\n` at top of file
- `abandoned` → `> Status: **abandoned**\n\n`
- On `reenterPlanMode` → regex `content.replace(/^> Status:.*\n\n?/, "")` strips it.

**Events** (`PlanEventType`): `"plan_mode_entered"`, `"plan_mode_exited"`, `"plan_created"`, `"plan_updated"` — each carries `{type, planId?, timestamp}`.

### 1.4 Sandbox (`src/planning/sandbox.ts`, rewritten)

Port from qdevbot `src/planning/sandbox.ts` (135 lines) — three exported wrappers plus one helper predicate. **Symlink-safe** predicate (qlaybot-specific hardening over qdevbot):

- `wrapWriteForPlanMode(tool, planManager, cwd)` — checks `params.path || params.file_path`, calls `isInsidePlansDir`, blocks if outside.
- `wrapEditForPlanMode(tool, planManager, cwd)` — identical predicate, different error phrasing (`"Cannot edit..."`).
- `wrapBashForPlanMode(tool, planManager)` — unconditional block when `inPlanMode`. Rationale comment: *"Bash is fully blocked because reliably distinguishing read-only commands from destructive ones is not feasible (pipes, subshells, aliases, etc.)"*.
- `isInsidePlansDir(filePath, plansDir, cwd)` — private helper. **Symlink-safe** version (addresses Codex finding: `normalize+resolve+startsWith` does NOT prevent `plans/link -> /etc`):
  ```typescript
  import { realpathSync } from "fs";
  import { resolve, normalize } from "path";
  
  function isInsidePlansDir(filePath: string, plansDir: string, cwd: string): boolean {
    const candidate = normalize(resolve(cwd, filePath));
    const plansAbs = normalize(resolve(cwd, plansDir));
  
    // Realpath each side if it exists; for non-existent paths walk up until an
    // ancestor exists, then realpath that ancestor and re-append the tail.
    const realCandidate = realpathUpwards(candidate);
    const realPlans = realpathSync(plansAbs); // plansDir must exist at check time
  
    return realCandidate === realPlans || realCandidate.startsWith(realPlans + "/");
  }
  
  function realpathUpwards(p: string): string {
    // Walk up ancestors until one exists, realpath that, then rejoin the tail.
    // Rejects if any resolved segment escapes outside the eventual plansDir.
    // (Details in implementation plan — TRD-testable via tmpdir symlinks.)
  }
  ```
  **TOCTOU mitigation**: the check is called immediately before `originalExecute`, so the attacker would need to swap the path between the sandbox wrapper and `fs.writeFile` inside the base tool — we do NOT further harden against this in 0.4.3 (documented as known limitation D-TOCTOU). Mitigation for 0.4.4+: use `open(path, O_NOFOLLOW)` + fd-based write in the base tool, out of scope for this release.
- `blocked(reason)` — returns `AgentToolResult` with `content[0].text = JSON.stringify({error: "plan_mode_restricted", message: reason, hint: "You are in plan mode. Only the plan file can be modified. Use exit_plan_mode to leave plan mode first."})`.

Wrappers compose after any background-execution wrapping. Order preserved from qdevbot `tools/index.ts:45-77`.

### 1.5 KLayout MCP gate (`src/tools/annotations.ts` + `src/planning/sandbox.ts`)

qdevbot wraps its single `instrmcp` proxy tool with `planManager` (see `src/tools/instrmcp.ts:158-169`). qlaybot routes KLayout tools through `MCPManager` + `klayout-client.ts`, and every KLayout tool is separately declared. Per **divergence D5** we do NOT migrate qlaybot's existing `{readonly, readwrite, backgroundable}` annotation shape. Strategy:

1. **Classify every MCP tool in `src/tools/annotations.ts`** — extend `TOOL_ANNOTATIONS` to ensure the following classification is explicit for every registered tool:
   - `readonly: true` (allowed in plan mode): `get_layout_info`, `screenshot`, `route_inspect`, `validate_pixel_size`.
   - `readwrite: true` (blocked in plan mode): `create_layout`, `save_layout`, `execute_script`, `auto_route`, `close_layout_view`, `evaluate_design`.
   - All klayout skill tools (geometry add_*, display toggle_*, image add_*/remove_*, nanodevice_*) → `readwrite: true`.
   - Any tool with no annotation entry → treated as deny-by-default.

2. **Namespaced-name normalization** (critical — Codex finding: qlaybot tools often have prefixes like `klayout_geometry_add_rect` while `TOOL_ANNOTATIONS` uses original names like `add_rect`):
   ```typescript
   // src/tools/annotations.ts (new export)
   export function canonicalToolName(registeredName: string): string {
     // Strip known namespace prefixes in the order they can appear.
     const PREFIXES = ["klayout_geometry_", "klayout_display_", "klayout_image_",
                        "klayout_visual_", "klayout_nanodevice_", "klayout_"];
     for (const p of PREFIXES) if (registeredName.startsWith(p)) return registeredName.slice(p.length);
     return registeredName;
   }
   
   export function getReadOnlyForPlanMode(registeredName: string): {
     allowed: boolean;
     reasons: string[];
   } {
     const canon = canonicalToolName(registeredName);
     const ann = TOOL_ANNOTATIONS.find(a => a.name === canon);
     if (!ann) return { allowed: false, reasons: [`no annotation for "${canon}"`] };
     if (ann.readonly) return { allowed: true, reasons: [] };
     if (ann.readwrite) return { allowed: false, reasons: ["readwrite: true"] };
     return { allowed: false, reasons: ["annotation present but neither readonly nor readwrite"] };
   }
   ```
   Unit tests MUST verify that every registered tool name (namespaced and bare) resolves correctly.

3. **Add `wrapMCPToolForPlanMode(tool, planManager)`** in `src/planning/sandbox.ts`, applied centrally in `src/tools/index.ts` immediately before tool-map return. When `inPlanMode`:
   ```typescript
   const { allowed, reasons } = getReadOnlyForPlanMode(tool.name);
   if (!allowed) return planModeBlockedTool(tool.name, reasons);
   // otherwise pass through
   ```
   `planModeBlockedTool(name, reasons)` returns:
   ```typescript
   {
     error: "plan_mode_restricted",
     tool: name,
     reasons,  // e.g. ["readwrite: true"] or ["no annotation for create_layout"]
     message: `Tool "${name}" is blocked during plan mode. Only readonly tools are allowed. Reasons: ${reasons.join(", ")}.`,
     hint: `Use exit_plan_mode to leave plan mode. To inspect a tool's annotation classification, check src/tools/annotations.ts.`,
   }
   ```

4. **Deny-by-default is centrally enforced**: `assembleTools` asserts that EVERY registered tool either goes through `wrapMCPToolForPlanMode` OR is explicitly on a small hardcoded allowlist (`read`, `memory_search`, `memory_save`, `enter_plan_mode`, `exit_plan_mode`, the three base-tool sandbox wrappers). A unit test in `test-plan-mode-v043.ts` enumerates the assembled tool map and verifies every tool is either wrapped or on the allowlist — fails loudly if a future tool is added without wrapping.

### 1.11 Subagents do NOT inherit plan mode — trust tradeoff

Mirror qdevbot `src/subagent/tool-factory.ts:1-45`. `src/subagent/runner.ts` must NOT pass `planManager` into `assembleTools` — subagents run with unrestricted tool access regardless of parent plan-mode state. Rationale: subagents are isolated ephemeral sessions with their own budget enforcement (maxTurns / maxTokens), and inheriting the parent sandbox would silently break subagent-based explorations the user dispatched during planning.

**Trust tradeoff (addresses Codex finding):** this leaves a parent-plan-mode-bypassing hole: while the parent is in plan mode, the parent agent could call `delegate` and the subagent could write/bash anywhere. 0.4.3 narrows the hole but does NOT fully close it:

1. **Gate `delegate` in parent plan mode.** The `delegate` tool wrapper checks `parentPlanManager.inPlanMode === true` and, if so, returns a blocked JSON: `{error: "plan_mode_restricted", tool: "delegate", message: "Cannot spawn a subagent during plan mode — subagents would bypass the sandbox. Exit plan mode first."}`.
2. **Subagents themselves never enter plan mode.** The `enter_plan_mode` tool is not registered in subagent tool maps (via `assembleTools({isSubagent: true})`).
3. This is documented in the TOOLS-section prompt paragraph so the agent is aware.

### 1.13 Policy for in-flight tool calls / background tasks at plan-mode entry

When `enter_plan_mode` fires while a background bash / MCP / subagent task is still running:

- In-flight tasks are **allowed to complete** (qlaybot does not cancel them). Their results are delivered normally even if they would have been blocked by the sandbox had they been started after `enter_plan_mode`.
- Rationale: cancellation is not reliably plumbed through the Pi-Agent SDK's background task API; trying to enforce it would add error-handling complexity disproportionate to the blast radius.
- UX: the TUI shows a SYSTEM_MESSAGE `"Plan mode activated — 2 in-flight tasks will complete with their pre-plan-mode permissions."` when `inFlightTasks > 0`.

## 2. TUI Image Render (Minor)

### 2.1 Module (`src/tui/image-render.ts`, new)

```typescript
export type ImageRenderMode = "iterm2" | "fallback";

export function detectImageRenderMode(): ImageRenderMode {
  const term = process.env.TERM_PROGRAM || "";
  if (term === "iTerm.app" || term === "WezTerm" || term === "vscode") return "iterm2";
  return "fallback";
}

export function renderInlineImage(base64: string, opts?: {
  width?: string;  // default "auto"
  height?: string; // default "auto"
}): string {
  // iTerm2 OSC 1337 escape
  const w = opts?.width ?? "auto";
  const h = opts?.height ?? "auto";
  return `\x1b]1337;File=inline=1;width=${w};height=${h};preserveAspectRatio=1:${base64}\x07`;
}

export function renderFallback(base64: string, outDir: string): string {
  // Decode to /tmp, return "[image saved: <path>]"
}
```

### 2.2 Size cap

Hard cap: decoded size > 2 MB → always use fallback (even in iTerm2, to avoid freezing the terminal). 2 MB chosen because iTerm2 reliably handles it; larger images flicker or stall on some hosts.

### 2.3 Image-block passthrough (prerequisite, addresses Codex finding)

**Current state** — qlaybot's MCP tool wrappers (`src/tools/index.ts` + MCP client path) collapse tool results to a text-only `content` field. `ToolPanel` never sees `{type: "image", ...}` today. Image rendering cannot work until image blocks are preserved through the pipeline.

**Required change before §2.4 is implementable:**

1. In `src/mcp/klayout-client.ts` and `src/mcp/transport.ts`, preserve every content block from the MCP tool response without flattening. Current code path that stringifies image payloads to `"[image]"` text must be replaced with a passthrough that returns `content: Array<{type: "text", text: string} | {type: "image", source: {type: "base64", media_type: string, data: string}}>`.
2. Extend the `MCPToolResult` interface in `src/mcp/types.ts` to include the image variant.
3. Extend the reducer's `ToolExecution` type so `result: unknown` becomes `result: MCPToolResult | BaseToolResult` with the image-block union preserved.

A unit test validates that `screenshot` tool responses round-trip through the MCP pipeline with the `image` block intact.

### 2.4 Integration (`src/tui/components/ToolPanel.tsx`)

Given §2.3, tool results reach `ToolPanel` via the reducer's `ToolExecution` object. When rendering the expanded result:

```typescript
for (const block of result.content ?? []) {
  if (block.type === "image") {
    const mode = detectImageRenderMode();
    if (mode === "iterm2" && base64DecodedSize(block.source.data) <= 2_000_000) {
      push(<Text>{renderInlineImage(block.source.data)}</Text>);

  }
}
```

## 3. Transcript Truncate (Minor)

### 3.1 Module (`src/truncation.ts`, new, shared)

```typescript
export interface TruncationOptions {
  threshold: number;  // max chars before truncation applies
  headChars: number;  // chars to keep from the start
  tailChars: number;  // chars to keep from the end
}

export const DEFAULT_TRANSCRIPT_TRUNCATION: TruncationOptions = {
  threshold: 2000,
  headChars: 1000,
  tailChars: 1000,
};

export function truncate(s: string, opts: TruncationOptions): string {
  if (s.length <= opts.threshold) return s;
  const head = s.slice(0, opts.headChars);
  const tail = s.slice(s.length - opts.tailChars);
  const hidden = s.length - opts.headChars - opts.tailChars;
  return `${head}\n... (truncated ${hidden} chars) ...\n${tail}`;
}
```

### 3.2 Integration (`src/history.ts`)

**Correction (v2)**: qlaybot's transcript schema uses entry type `"tool_call"` (see `src/history.ts:14,126`) — there is no separate `"tool_result"` entry today. The `result` is a nested field inside the `tool_call` entry: `{type: "tool_call", toolName, args, result, durationMs, timestamp}`. The earlier spec incorrectly referenced a non-existent entry type.

`InteractionHistory.recordToolCall(toolName, args, result, durationMs)` currently writes two places:
1. A line to `transcript.jsonl` with `type: "tool_call"`.
2. A full JSON file `tool_calls/NNN_{toolName}.json` with the same shape.

Change:
- Inside `recordToolCall`, run `truncate(serializedResult, DEFAULT_TRANSCRIPT_TRUNCATION)` on the **`result` field only**. Args are untruncated (bounded by model output).
- `result` serialization: if already a string → truncate directly; else `JSON.stringify(result, null, 2)` → truncate. Preserve the JSON string (not re-parse).
- Apply to BOTH the transcript.jsonl line AND the per-tool JSON file (single source of truth — the full result is NOT preserved anywhere on disk unless `--verbose` is on).
- Non-`tool_call` entry types (`user_prompt`, `agent_response`, `agent_thinking`, `tool_result` if any, `error`) are never truncated — these are bounded by model output or error messages.
- Schema additions (non-breaking): `tool_call` entries may now include `truncated: true` and `original_length: number` metadata fields so consumers can detect truncation. Old consumers ignore unknown fields.

### 3.3 Verbose override

`--verbose` → pass `{threshold: Infinity}` (or skip the `truncate` call). Handled by a config lookup, not a separate code path.

### 4.3 Effects

1. **Disable TUI truncation** in `ToolPanel.tsx` — skip the 8-head/8-tail `formatResult` branch, render full result. `ToolPanel` gets a `verbose: boolean` prop sourced from App-level context.
2. **Disable transcript truncation** in `history.ts` — see §3.3. Plumb: CLI flag → `QlayBotConfig.verbose` → `createDesignSession({...config})` → `InteractionHistory` constructor → call-site check.
3. **Print system prompt on startup** — requires exposing the assembled prompt. The prompt is built in `agent.ts` by `buildSystemPrompt(ctx)` but not currently returned on the session object. Add to the `QlayBotSession` type a new field `assembledSystemPrompt: string` set during session creation. In `App.tsx` post-init effect (`useEffect(() => { if (verbose) dispatch({type: "SYSTEM_MESSAGE", text: botSession.assembledSystemPrompt}); }, [])`). Guard: only if `verbose === true`.
4. **Per-turn timing + token usage** — requires event-payload exposure. Inspect the Pi-Agent SDK's `agent_end` event to confirm `usage` is in the payload; if it's not, add a `timing` field `{turnMs: number}` to the event subscription bridge (`src/events.ts`) by wrapping subscription and tracking `agent_start`→`agent_end` deltas in the bridge. Token counts come from `session.lastTurnUsage` (verify field on `AgentSession` — if absent, file as prerequisite TRD task before implementing this effect). Dispatch:
   ```
   SYSTEM_MESSAGE: [turn {n}: {elapsedMs}ms, in={inputTokens}, out={outputTokens}, thinking={thinkingTokens}]
   ```
   If token counts are not exposed by the SDK, emit only timing: `[turn {n}: {elapsedMs}ms]`.
5. **Project transcript copy** — new `src/verbose-transcript.ts`. On session start, open `${workspaceDir}/qlaybot-transcripts/{sessionId}-{YYYYMMDD-HHMMSS}.jsonl` in append mode (`fs.createWriteStream` with `flags: "a"`). One file per session, written line-by-line as events arrive. **Durability** (addresses Codex finding): use async writes with no `fsync` — the file is crash-safe in the weaker sense of "every fully-written line is valid JSON, but the last few lines may be lost on OS crash". We do NOT claim fsync durability (that would violate the §5.4 30 ms-per-write budget). Mirrors every event written to `~/.qlaybot/history/.../transcript.jsonl` but with NO truncation applied. Close on session end via `stream.end()` and await `finish` event. Cleanup: no auto-delete (user manages). Parent dir `${workspaceDir}/qlaybot-transcripts/` created on first write; if unwritable, log an error once to stderr and silently skip subsequent writes (don't break the session for an optional feature). **Backpressure**: if `stream.write()` returns false, queue events in memory until `drain` — drop events with a stderr warning if the queue exceeds 1000 entries (avoids unbounded memory in pathological cases).

### 4.5 Non-TUI mode behavior

For `--mode json` and `--mode rpc`, `--verbose` toggles:
- Transcript truncation disabled (same as TUI).
- Project transcript copy written (same as TUI).
- System prompt + per-turn stats NOT emitted to stdout (would corrupt JSON protocol output). In JSON mode, if verbose, these are written to stderr only.
