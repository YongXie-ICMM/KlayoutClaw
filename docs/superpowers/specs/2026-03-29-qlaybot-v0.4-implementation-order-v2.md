## What Failed in v1 and Why

### Problem 1: Group isolation killed integration
Each TRD group ran only its own test file (`Do NOT run full npm test`). Result: each group's code compiled and passed its own tests, but groups didn't compose at runtime. Hundreds of integration errors on merge.

**Fix:** Accumulative testing. Every group must pass ALL prior group tests + its own + `npm run build`. No exceptions.

### Problem 2: Agents satisfied tests, not specs
TRD makes the Overseer write tests and the Executor pass them. Neither agent is incentivized to verify ALL spec details — only what the Overseer happened to test. For TUI features (keyboard shortcuts, focus transitions, visual states), the Overseer wrote surface-level tests and the Executor implemented just enough to pass.

**Fix:** Each group prompt includes a **Spec Compliance Checklist** — a literal enumeration of every non-obvious behavior from the spec that MUST be verified. The Overseer MUST write a test for each checklist item. The Executor MUST verify each item works.

### Problem 3: Frontend "can't be tested" became excuse to skip
TUI components have dozens of behaviors (keyboard events, focus routing, rendered output). Agents skipped them because "TUI is hard to test."

**Fix:** Concrete testing patterns for every TUI behavior category:
- **Reducer tests** for state machines (pure functions, fully testable)
- **ink-testing-library** `render()` + `frames` for visual assertions
- **`stdin.write()`** for keyboard event simulation
- **State-then-render** pattern: test transitions separately from rendering

## Accumulative Test Gates

**This is the critical change from v1.** Two-tier testing:
- **Iteration gate** (every TRD cycle): `npm run build` + own test file only — keeps velocity
- **Exit gate** (once, when declaring DONE): `npm run build` + all prior tests + own — catches regressions

The table below shows the **exit gate** command for each group.

| 2 | C | contracts + config-tui + config-tui-components | `npx vitest run tests/test-contracts.ts tests/test-config-tui.ts tests/test-config-tui-components.ts` |

## Spec Compliance Protocol

Each TRD group prompt includes a **Spec Compliance Checklist** (SCC). These are behaviors the spec defines that are easy to miss:

### How SCC works:

1. **Overseer reads the SCC** and writes at least one test per checklist item
2. **Executor implements** to pass those tests
3. **Before declaring done**, agent runs the gate command AND manually reviews the SCC items against the code

### SCC categories:

| Category | What to test | Testing pattern |
|----------|-------------|-----------------|
| Config shape | All fields present with correct types/defaults | `typeof` + `JSON.parse` round-trip |
| State machine | All transitions between states | Reducer dispatch → assert new state |
| Keyboard events | Every shortcut from the spec | `stdin.write('\x13')` for Ctrl+S, etc. |
| Visual output | Specific strings/icons in rendered output | `stripAnsi(frames[last]).toContain(...)` |
| Focus routing | Priority order (completion > bar > history) | Dispatch KEY_UP in each focus state |
| Error paths | Invalid input, missing config, API failure | Pass bad data → assert error message |
| Integration seams | Exported functions callable with correct args | Import + call with mock args |

## TUI Testing Patterns (mandatory for Groups 2, 3, 5)

### Pattern 1: Reducer State Machine Test
```typescript
// Test focus transitions as pure functions — no rendering needed
it("Down from empty input enters bar-select", () => {
  const state = { ...init, focusState: "input", inputText: "" };
  const next = tuiReducer(state, { type: "KEY_DOWN" });
  expect(next.focusState).toBe("bar-select");
});

it("Down from non-empty input navigates history", () => {
  const state = { ...init, focusState: "input", inputText: "hello" };
  const next = tuiReducer(state, { type: "KEY_DOWN" });
  expect(next.focusState).toBe("input"); // Stays in input
});
```

### Pattern 2: Ink Component Render Test
```typescript
import { render } from "ink-testing-library";

it("ConfigPanel shows active tab bracketed", () => {
  const { lastFrame } = render(<ConfigPanel tab="settings" />);
  const output = stripAnsi(lastFrame()!);
  expect(output).toContain("[Settings]");  // Active
  expect(output).toContain(" Models ");     // Inactive
  expect(output).toContain(" MCP ");        // Inactive
});
```

### Pattern 3: Keyboard Event Simulation
```typescript
it("Tab switches ConfigPanel tab", () => {
  const { stdin, lastFrame } = render(<ConfigPanel tab="settings" />);
  stdin.write("\t"); // Tab key
  const output = stripAnsi(lastFrame()!);
  expect(output).toContain("[Models]");  // Tab advanced
});
```

### Pattern 4: Combined State + Render
```typescript
it("Ctrl+S opens SubagentPanel", () => {
  const { stdin, lastFrame } = render(<App {...mockProps} />);
  stdin.write("\x13"); // Ctrl+S
  expect(lastFrame()).toContain("Subagents"); // Panel visible
});
```
