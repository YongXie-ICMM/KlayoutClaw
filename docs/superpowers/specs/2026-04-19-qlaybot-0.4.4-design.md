# qlaybot v0.4.4 — Design Spec

**Originally drafted:** 2026-04-19
**Finalised:** 2026-04-20
**Status:** Ready for implementation plan
**Scope:** Three additive features on top of v0.4.3, split across two release tracks.

---

## 1. Overview

v0.4.4 adds three capabilities to the qlaybot / KlayoutClaw stack:

1. **`thinking` tool** — a side-effect-free scratchpad tool the agent calls to externalise reasoning between tool calls. Agent-side, TypeScript.
2. **Plan-mode execution** — extend v0.4.3 plan mode so that, on approval, the agent auto-executes the approved plan in the same session. Agent-side, TypeScript.
3. **KLayout version control** — Git-like version control for `.gds` layouts, with a KLayout UI panel, sidecar storage, deterministic serialisation, and new MCP tools for agent-driven history navigation. Plugin-side (Python) + MCP surface.

### 1.1 Release gate (staged)

| Track | Features | Gate | Slip target |
|-------|----------|------|-------------|
| Track 1 (core) | `thinking`, plan-mode execution | Must ship for v0.4.4 | — |
| Track 2 (extension) | KLayout version control | Ships in v0.4.4 if Track 2 E2E passes | v0.4.5 |

If Track 2 slips, v0.4.4 ships with Tracks 1 only and v0.4.5 picks up VC unchanged.

### 1.2 Non-goals for v0.4.4

- No changes to the underlying model or reasoning-token budget.
- No new subagent roles.
- No changes to existing v0.4.3 MCP tools (the ten listed in `docs/tools.md`); new VC MCP tools are additive.
- No multi-user concurrent editing or remote git push/pull.
- No OASIS-primary VC support (GDSII primary; OASIS via conversion).
- No mid-execution human checkpoint approvals; execution runs to completion or re-drafts on blocker.
- No structured reflection logs (hypothesis/evidence/decision schema) on top of `thinking`.
- **No subagent plan-mode support in v0.4.4.** The existing v0.4.3 behaviour is preserved: `agent/src/tools/delegate.ts:40-53` blocks subagent dispatch while the parent is in plan mode ("Cannot spawn a subagent during plan mode — subagents would bypass the sandbox"). Subagent plan-mode + approval-gate infrastructure (mailbox, `awaitingPlanApproval` task state, `plan_approval_request/response` transport, `planModeRequired` flag) is deferred to v0.4.5. Rationale: qlaybot's `SubagentRunner` is run-to-completion and synchronous; introducing mid-run approval queues is a separate architectural shift that deserves its own release.

### 1.3 Cross-feature integration

All three features are **loosely coupled via system-prompt guidance only**. Shared runtime state is limited to:

- A namespaced transcript-marker schema (`think_*` for Track 1 thinking tool, `plan_*` for Track 1 plan mode) that the TUI and verbose transcript renderers consume. Track 2 (VC) emits **no dedicated transcript markers in v0.4.4** — VC observability lives entirely in tool-call results (per the agent-first scoping in §5.1). If downstream renderers want per-VC-event chips, they derive them from the structured tool-completion signals for `klayout_native_vc_*` calls (on the TUI side, the `onToolEnd` callback fired by `subscribeToSession`; on the `-m` JSON-RPC wire, the `tool_result` event at `agent/src/rpc.ts:217` — these are the same logical event in two layers); see §7.5.
- Prompt text that encourages `klayout_native_vc_checkpoint` before destructive ops during `plan_executing`, and `klayout_native_vc_checkout` on execution failure.

No hard-coded hook wires one feature into another. If VC is unavailable (transient mode off, repo not initialised), Track 1 still functions; the agent's VC-related prompt guidance silently no-ops.

Key architectural invariants:

- **No shared runtime state across tracks.** Only the transcript-marker schema and system-prompt text cross the boundary.
- **Track 2 is optional at runtime.** Track 1 must work when `klayout_native_vc_init` has never been called.
- **Transcript markers are namespaced.** Readers silently ignore markers they don't understand, which keeps the schema forward-compatible.
- **Plan immutability between draft and execute.** The plan text shown to the user/agent for approval is byte-equal to the plan that enters `plan_executing`.

### 2.1 Tool-name conventions

Tool names follow the Anthropic API regex `^[a-zA-Z0-9_-]{1,64}$` — underscores, no dots. qlaybot's existing namespacing (see `agent/src/mcp/klayout-client.ts`, `agent/CLAUDE.md`) splits tools into three categories. **Every example, prompt snippet, and E2E test in this spec uses the agent-facing form; tables that describe KLayout plugin registration use the bare plugin-RPC form, which is then prefixed automatically at registration time.**

| Category | Agent-facing name (what the model sees in `tools/list`) | Where defined |
|----------|---------------------------------------------------------|----------------|
| Agent built-ins | bare (`read`, `bash`, `edit`, `write`, `memory_save`, `memory_search`, `delegate`, `thinking`, `enter_plan_mode`, `exit_plan_mode`) | `agent/src/tools/*.ts` |
| Native KLayout MCP | `klayout_native_<rpc_name>` (e.g. `klayout_native_execute_script`, `klayout_native_auto_route`, `klayout_native_save_layout`, `klayout_native_get_layout_info`, `klayout_native_screenshot`, `klayout_native_route_inspect`, `klayout_native_evaluate_design`, `klayout_native_close_layout_view`, `klayout_native_validate_pixel_size`, `klayout_native_create_layout`) | Plugin `plugin/klayoutclaw_server.lym` registers the bare name; `KLayoutMCPClient.allTools()` prefixes with `klayout_native_` |
| Domain KLayout skill | `klayout_<group>_<name>` (e.g. `klayout_geometry_add_rect`, `klayout_display_toggle_layer`, `klayout_image_add_image`, `klayout_visual_capture`, `klayout_flakedetect_align`) | `agent/src/tools/klayout/<group>/*.ts` |

New v0.4.4 KLayout-plugin tools land in the native category and are agent-visible under the `klayout_native_` prefix. For example, Feature 3's VC tools are registered in the plugin as `vc_init`, `vc_checkpoint`, `vc_history`, …; the agent calls them as `klayout_native_vc_init`, `klayout_native_vc_checkpoint`, `klayout_native_vc_history`, …. **Bare plugin-RPC names are permitted only in plugin-side surfaces: (a) the §2 architecture diagram (labelled), (b) all of §5.2 (Components) — which describes plugin-internal requirements, interface contracts, UI-hotkey triggers, and plugin registration schema, (c) §8.2 failure-mode table (plugin-side behaviour), (d) §9.4 Plugin UI tests (which exercise the plugin's own Python dispatch, not the agent's MCP client), and (e) §4.5 Inspect/Pattern columns and the envelope recap, which discuss plugin-side payload fields and error shapes (not agent tool-call names). Everywhere else — §3, §4.1-4.4, §4.6-4.8, §6, §7, §8.1, §8.3, §9.1-9.3, §9.5, §11, §12 — uses the agent-facing `klayout_native_*` / `klayout_<group>_*` form.**

## 3. Feature 1 — `thinking` tool (Track 1)

> **Framing.** The v0.4.4 `thinking` tool is an **additive, side-effect-free scratchpad** that the qlaybot agent exposes as a discrete function-call tool. It is **not** a replacement for, and does **not** modify, the two pre-existing reasoning surfaces that the reference codebases already rely on:
>
> 1. **Native Anthropic extended-thinking content blocks** (`type: "thinking"` / `type: "redacted_thinking"` with cryptographic `signature` fields, produced by the model via `BetaMessageStreamParams.thinking` in Claude Code and via `output_config.effort` / `THINKING_BUDGET` in Hermes's `anthropic_adapter.py`).
> 2. **Inline `<think>` / `<reasoning>` tags** emitted in the model's own content stream (handled by Hermes's `stream_consumer.py` state machine and the `splitReasoning` TUI helper).
>
> The `thinking` tool sits *on top of* those surfaces. The model may call it in the same turn that it also emits a native thinking block; the two are independent and must not alias each other in transcripts, in compaction, or in any signature-handling path. The schema below is deliberately minimal (one string in, a no-op echo out) by user decree — no effort dial, no structured schema, no budget knob. Effort lives on the model (via the host's own thinking config); the tool is just a transcript-level marker the agent controls.

### 3.1 Purpose

Give the agent a dedicated, side-effect-free place to externalise intermediate reasoning ("what have I verified, what am I about to try, why") as an explicit tool call. This produces:

- a cleaner interleave between reasoning and action in the transcript,
- a marker the TUI and verbose transcript renderer can anchor on,
- a hook point for future telemetry / evaluation,
- a reasoning surface that is preserved even when the underlying model does not emit native thinking blocks (e.g. third-party endpoints where Hermes strips signed thinking — see `_extract_preserved_thinking_blocks` and the base-URL-based signature-stripping path in `convert_messages_to_anthropic`).

### 3.3 Interface

```text
tool name:    "thinking"
description:  "Record a reasoning step. Side-effect-free scratchpad.
               Does not run code, does not call other tools, does not
               change layout state. Use to externalise what you've
               verified and what you're about to try."
input_schema: {
  type: "object",
  additionalProperties: false,
  required: ["thought"],
  properties: {
    thought: { type: "string", minLength: 1 }
  }
}
output:       { ok: true, thought: <verbatim echo of input thought> }
transcript:   { type: "think_recorded",
                source: "tool",
                thought: string,
                ts: iso8601 }
```

The echoed `thought` on the output satisfies the "echoes the exact same tokens back" contract and makes the tool trivially verifiable in tests (T1(c) in §9 checks that the result payload contains the input verbatim).

### 3.4 Prompt guidance (wording finalised in impl plan)

Short, concrete list — loosely inspired by Claude Code's `ultrathink` keyword trigger model (a single lexical anchor that flips behaviour) rather than by Hermes's multi-level `/reasoning` menu. The tool has no effort dial, so the guidance is purely about *when* to call it:

- Call `thinking` before any destructive MCP call (`klayout_native_save_layout`, `klayout_native_auto_route`, `klayout_native_execute_script` that mutates geometry, `klayout_native_vc_checkpoint`, `klayout_native_vc_checkout`).
- Call `thinking` when choosing between two or more viable approaches, when resolving an ambiguity in the user's request, or when interpreting a surprising tool result.
- Do not call `thinking` for trivial single-step requests (TH-12 / T7).
- One thought per call; keep each call tight. Prefer two short `thinking` calls over one long one if the decisions are independent.
- During `plan_executing`, reference the active VC branch / checkpoint when it is load-bearing for the decision (see §6 cross-track integration).
- Do not paste raw tool output back into `thought`; summarise the decision, not the data.

### 3.6 Interaction with native extended thinking

Explicit invariants when the host model emits native thinking blocks in the same turn as a `thinking` tool call:

1. **Ordering is preserved as-emitted.** If the model emits a native `thinking` block, then a `thinking` tool call, then a text reply, the transcript contains three markers in that order (`source:"native"`, `source:"tool"`, free text), not one merged marker.
2. **No marker coalescing.** The harness must not concatenate the `thinking` native-block `thinking` field with the `thought` tool argument, even if they are textually similar.
3. **Signature preservation on native blocks continues to work.** When Hermes-style cross-turn carry-over is active (`_extract_preserved_thinking_blocks`), only blocks with `type ∈ {thinking, redacted_thinking}` are eligible. `tool_use` blocks for `thinking` never match this filter (TH-10).
4. **Third-party endpoint stripping is unaffected.** Hermes strips native thinking blocks wholesale on third-party base URLs. `thinking` tool calls are ordinary tool calls and are not stripped by that path, which is exactly why the tool is valuable on such endpoints (see §3.1 bullet 4).

### 3.7 Edge cases

| Case | Handling |
|------|----------|
| `thought` is the empty string | Schema validation fails (TH-2 `minLength: 1`); tool returns a validation error and no `think_recorded` marker is emitted. |
| `thought` contains literal `<think>...</think>` substrings | Passed through verbatim in the transcript marker and in the echoed result. TH-11 guarantees the stream-level tag parser never sees it; the renderer must treat the field as opaque. |
| `thought` contains JSON-escaped tool-call-looking fragments | Opaque; not parsed. Only the top-level `tool_use` schema is honoured. |
| Agent calls `thinking` rapidly back-to-back (e.g., 5× in one turn) | Permitted. Each call emits one `think_recorded` marker. `microCompact` may later summarise them (TH-13) but does not change real-time behaviour. |
| Agent calls `thinking` in `plan_drafted` state | Rejected by the harness per TH-7 / PM-8 with a state-violation error; no marker emitted. |
| Model also emits a native `thinking` content block in the same turn | Both surfaces coexist independently per §3.6. Transcript distinguishes via the `source` field (TH-9). |
| Third-party Anthropic-compatible endpoint strips native thinking | `thinking` tool calls still flow end-to-end because they are ordinary `tool_use` blocks, not signed thinking blocks (TH-10). |
| `thinkingClearLatched` / `clearAllThinking` is asserted by the host | Native thinking blocks are cleared per host policy. `think_recorded` markers are NOT promoted to native blocks and are NOT retroactively cleared by this flag (TH-13). |

## 4. Feature 2 — Plan-mode execution (Track 1)

### 4.1 Purpose

v0.4.4 extends qlaybot's existing plan-file-driven plan mode (v0.4.3, implemented in `agent/src/tools/plan.ts` + `agent/src/planning/`) with an explicit user-approval gate, so that on approval the agent auto-executes the approved plan in the **same** session.

**v0.4.3 baseline (partially replaced in v0.4.4).** The plan lives in a file on disk, not as a tool-call argument. The identifier is generated **at entry time**, not at exit. The v0.4.3 lifecycle is:

1. Agent calls `enter_plan_mode({task, reason?})` → `PlanManager.enterPlanMode` (a) generates a timestamp-based identifier `plan-${Date.now()}` with a 10-slot collision loop appending `-1` through `-9` on conflict (`agent/src/planning/index.ts:52-83`; throws on exhaustion), (b) creates `<plansDir>/<identifier>.md` **immediately**, (c) stores the plan handle in `PlanManager._currentPlan`, (d) returns `{status: "plan_mode_active", plan_id, plan_file, instructions, task, reason}` with the concrete `plan_file` path.

**v0.4.4 refactors step 1.** The timestamp identifier is replaced by a **word-slug** cached by a new **`PlanSlugCache`** abstraction (PM-12: internally a `WeakMap<AgentSession, string>`, surface API `{get/set/delete}`), with a structured error on 10-retry exhaustion. See PM-11 for the exact contract. The enter tool's return shape is unchanged; `plan_file` simply resolves to `<plansDir>/<word-slug>.md` instead of `<plansDir>/plan-<ts>.md`. Existing on-disk files from v0.4.3 sessions remain readable; new sessions always use word-slugs.
2. Sandbox (`agent/src/planning/sandbox.ts`) wraps `read` / `write` / `edit` / `bash` and every MCP tool. Permitted: (a) tools annotated `readonly: true` in `agent/src/tools/annotations.ts`; (b) `read` — globally allowed (read-anywhere), no path scoping; (c) `write` / `edit` — scoped to **any path under `<plansDir>/`** (per `isInsidePlansDir` at `sandbox.ts:128-140` / `:154-173`). The `plan_file` returned by `enter_plan_mode` is the conventional target; sibling paths under `<plansDir>/` are also writable by design (not a bug). `bash` is blocked entirely. **Not** plan-file-scoped — see §4.2 invariants.
3. Agent repeatedly reads layout state (`klayout_native_get_layout_info`, `klayout_native_screenshot`, `klayout_native_route_inspect`, `klayout_native_validate_pixel_size`, `memory_search`) and writes/edits the plan file at the `plan_file` path returned in step 1.
4. Agent calls `exit_plan_mode({approved?: bool, summary?: string})` → returns `{status: "plan_approved" | "plan_abandoned" | "not_in_plan_mode" | "error", plan_id, plan_file, summary?, message}`. On `plan_approved`, sandbox is lifted in-session and the agent proceeds. There is **no** user-approval gate in v0.4.3.

**Tool-result vs gate outcome (v0.4.4).** The `exit_plan_mode({approved: true})` behaviour differs by mode:

- **Interactive TUI (main agent).** The tool `execute()` blocks inside `await waitForPlanApproval(session)` (§4.4 pause/resume mechanism), so the tool-result is returned only AFTER the user picks an action. In this mode the tool-result IS authoritative for the gate decision: `status: "plan_approved"` with `executeAfterApproval: true` means option 1, `executeAfterApproval: false` means option 2, `status: "plan_rejected"` means option 3, `status: "plan_abandoned"` means option 4. Markers emitted before the tool returns give observers real-time progress; markers and tool-result agree.
- **Headless `-m` (main agent).** No gate (PM-4). The tool returns immediately with `{status: "plan_approved", ...}` after emitting `plan_drafted` + `plan_file_written` + `plan_approved {auto: true, executeAfterApproval: true}`. The tool-result means "drafting complete; headless auto-resolved to `approve_execute`". The authoritative signal for whether `plan_executing` ran to `plan_done` is still the marker stream — callers should observe `plan_done` before considering the turn complete.

**All callers SHOULD observe the marker stream for turn-completion**, regardless of mode. Tool-result is sufficient for per-call gate-decision inspection but does NOT report execute-path completion (which happens after the tool returns).

**v0.4.4 delta.** Insert a **TUI-only** user-approval gate between the agent's `exit_plan_mode({approved: true})` result and sandbox lift. The gate surfaces a **4-option menu** (accept-and-execute / accept-without-execute / reject-with-feedback / abandon). Headless `-m` mode has **no gate** in v0.4.4 (PM-4): `exit_plan_mode({approved: true})` auto-executes; `exit_plan_mode({approved: false})` remains the abandon shortcut. Gated headless approval (caller submits action via a new RPC method) is v0.4.5 work (OQ-7). The tool contract is NOT changed: `exit_plan_mode` still takes `{approved?, summary?}`; the plan payload still lives in the plan file.

**Key invariant.** The "plan text" referred to throughout this spec is **the bytes of the plan file** at the moment of `exit_plan_mode` — not any string argument. PM-5's hash chain is computed over those file bytes, not over a parameter.

### 4.2 State machine

Six states; marker namespace is `plan_*` (do not rename). Entry/exit invariants below are normative.

| State | Enter on | Exit on | Tools allowed |
|-------|----------|---------|----------------|
| `plan_drafting` | agent calls `enter_plan_mode({task, reason?})`; `PlanManager.enterPlanMode` creates the plan file and returns `{status: "plan_mode_active", plan_file, plan_id, instructions}` | agent calls `exit_plan_mode({approved?, summary?})`. With `approved=true`: transitions only if the plan file is non-empty (empty-plan `exit_plan_mode({approved: true})` returns `{status: "error", message: "Plan file is empty; abandon or continue drafting"}` and stays in `plan_drafting`). With `approved=false`: **always** transitions to the abandon terminal `plan_rejected {action: "abandon"}` per PM-2, regardless of plan-file contents. | `read`, `memory_search`, `thinking`, all tools annotated `readonly: true` in `agent/src/tools/annotations.ts` (`klayout_native_get_layout_info`, `klayout_native_screenshot`, `klayout_native_route_inspect`, `klayout_native_validate_pixel_size`), AND scoped `write`/`edit` to any path under `<plansDir>/` (matches current v0.4.3 sandbox per `agent/src/planning/sandbox.ts:128-140` and `:154-173` — `plansDir`-scoped, not single-file-scoped). Subagent plan mode is out of v0.4.4 scope (PM-9). |
| `plan_drafted` | `exit_plan_mode` returns `status: "plan_approved"` with a non-empty plan file on disk (`approved=true` is the agent's drafting-complete signal — the user-facing approval gate is separate, §4.4) | approval decision arrives (interactive TUI gate) OR `-m` auto-approval fires immediately per PM-4 | **none** (hard freeze — see PM-8) |
| `plan_approved` | approval granted (interactive `approve_execute` / `approve_only`, or `-m` default auto-execute per PM-4 — `-m` only ever produces `approve_execute`) | `plan_executing` if `executeAfterApproval=true`; **end of turn** if `executeAfterApproval=false` (the draft-only path — this is the turn's terminal marker, no `plan_done` is emitted on this branch) | n/a |
| `plan_rejected` | rejection (interactive TUI `reject` / `abandon` gate options, OR `exit_plan_mode({approved: false})` abandon-shortcut per PM-2). `-m` mode cannot reach this state via a gate action in v0.4.4 (deferred to v0.4.5 per OQ-7). | `plan_drafting` if `action="reject"`; **end of turn** if `action="abandon"` (abandon is the turn's terminal marker, no `plan_done` is emitted on this branch) | n/a |
| `plan_executing` | `plan_approved` with `executeAfterApproval=true` | plan completes successfully OR unrecoverable blocker | all permitted tools (per the restored pre-plan permission context) |
| `plan_done` | execution finishes (only on the execute path) | end of turn | — |

State invariants:
- `plan_approved` and `plan_rejected` are **instantaneous transitions**; no tool call executes while in these states. They exist solely to carry an approval/rejection marker.
- `plan_drafting` ↔ `plan_executing` transitions must pass through `plan_drafted` and an approval marker. Direct transitions are a **harness protocol violation** and are treated as a fatal session error: the harness raises `PlanProtocolError("illegal state transition: <from> → <to>")`, emits `plan_rejected {feedback: "protocol violation: illegal state transition", action: "abandon"}` as the turn's terminal marker (satisfies the terminal-marker invariant (§4.2)), and surfaces the error to the caller. No `plan_done` is emitted — `plan_done` is reserved for the execute path only (turn began in `plan_executing`).
- The permission context during `plan_drafting` and `plan_drafted` MUST be a **plan-mode context** (analogous to Claude Code's `toolPermissionContext.mode = 'plan'`; see PM-10). This context is "read-only with one exception": `write` / `edit` are permitted for any path under `<plansDir>/` (`plansDir`-scoped, matching `agent/src/planning/sandbox.ts:128-140` and `:154-173` — `isInsidePlansDir` is the predicate). All other `write`, `edit`, `bash`, and tools annotated `readwrite: true` remain blocked. Rationale for `plansDir`-scoped (not single-file-scoped): the v0.4.3 sandbox already allows any file in `plansDir`, and there is no concrete v0.4.4 requirement that motivates tightening. If a tightening becomes needed in v0.4.5+ (e.g. to prevent an agent from writing sibling plan files), it would be a separate refactor of `sandbox.ts`.
- **Turn termination is path-specific.** A user turn ends on **exactly one** of these three terminal markers (never zero, never more than one):
  - `plan_done` with `status: "ok"` or `"failed"` — execute path (approve_execute leading to `plan_executing` to completion or to cap-exhausted replan).
  - `plan_approved` with `executeAfterApproval: false` — draft-only path (reachable only via option 2 in the interactive TUI gate; `-m` mode always auto-executes per PM-4).
  - `plan_rejected` with `action: "abandon"` — abandon path (option 4 in the interactive TUI gate, OR `exit_plan_mode({approved: false})` shortcut per PM-2 — available in both TUI and `-m`).
- `plan_done` is emitted **only** on the execute path; it never appears on draft-only or abandon paths. Intermediate aborts during the replan loop are signalled by `plan_execution_aborted` (see §4.5, §4.6) and do not terminate the turn.
- **Disconnect and timeout semantics.** v0.4.4 has no gated headless path (PM-4), so there is no "caller idles at a gate" scenario to terminate. If a `-m` JSON-RPC caller disconnects during `plan_executing`, normal session-termination applies (existing v0.4.3 behaviour). Disconnect handling for the gated headless path is a v0.4.5 deliverable (OQ-7).

### 4.4 Approval semantics

The approval contract is **mode-dependent**. The 4-option action vocabulary (`approve_execute`, `approve_only`, `reject`, `abandon`) exists **only in the interactive TUI gate in v0.4.4**. Headless `-m` and subagents have a narrower, distinct surface:

- **Interactive / TUI (main agent)** — the 4-option menu opens on every `exit_plan_mode({approved: true})`. All four actions are reachable.
- **Headless `-m` (main agent)** — **no gate in v0.4.4**. The harness treats `exit_plan_mode({approved: true})` as an implicit `approve_execute` and runs straight through to `plan_executing`. The only other headless path is `exit_plan_mode({approved: false})` → abandon shortcut (PM-2 path B). `approve_only` / `reject` / explicit `abandon` via gate input do **not** exist on the `-m` path in v0.4.4. `autoApprovePlans` is fixed at `true`; a `false` setting is warned at startup and coerced to `true` (PM-4). The gated headless path is v0.4.5 work (OQ-7).
- **Subagents** — cannot enter plan mode in v0.4.4 (PM-9, §1.2 non-goal). The existing `delegate` gate preserves v0.4.3 behaviour: any `delegate` call during parent plan mode returns `plan_mode_restricted`. Subagent plan mode is a v0.4.5 deliverable.

The 4 gate actions are **interactive TUI only in v0.4.4**. Headless `-m` mode has no gate (PM-4): `exit_plan_mode({approved: true})` is always an implicit `approve_execute`; `exit_plan_mode({approved: false})` is the abandon shortcut. `approve_only` / `reject` / explicit `abandon` via gate input do not exist on the `-m` path (deferred with OQ-7).

| Action code | TUI accelerator (suggested) | Emitted marker | Next state | Sandbox | Terminal for turn? |
|-------------|----------------------------|-----------------|-------------|---------|---------------------|
| `approve_execute` | `1` / Enter / `yes`, `y`, `go`, `/go`, `ok`, `okay`, `approved`, `approve` | `plan_approved {auto, executeAfterApproval: true}` | `plan_executing` | lifted (pre-plan context restored, PM-10) | No — terminal marker is `plan_done` at end of execution |
| `approve_only` | `2` / e.g. `/draft` | `plan_approved {auto, executeAfterApproval: false}` | end of turn | lifted | **Yes** — this marker terminates the turn; no `plan_done` emitted |
| `reject` | `3` / any non-affirmative free text | `plan_rejected {feedback, action: "reject"}` | `plan_drafting` | stays active | No — replan loop continues |
| `abandon` | `4` / e.g. `/abandon` | `plan_rejected {feedback: "abandoned", action: "abandon"}` | end of turn | lifted (plan mode ends — `PlanManager.exitPlanMode(false)` is called, `inPlanMode` becomes `false`; the next user turn starts outside plan mode) | **Yes** — this marker terminates the turn; no `plan_done` emitted |

**Interactive / TUI mode:**
- Render the 4 options alongside the plan-file preview. Free-text affirmative tokens listed in the table above map to `approve_execute`.
- Anything that isn't an accelerator or affirmative token is treated as `reject` feedback (raw text → `feedback`).

**Headless `-m` / JSON mode (main agent):** no gate in v0.4.4. The harness auto-approves with `approve_execute` semantics, emits `plan_approved {auto: true, executeAfterApproval: true}`, and transitions to `plan_executing` synchronously. `autoApprovePlans: false` is a v0.4.5 config (OQ-7); if set in v0.4.4 the harness logs a warning and behaves as `true`. Headless callers who need "plan without execute" use `exit_plan_mode({approved: false})` (abandon shortcut).

**TUI pause/resume mechanism (interactive gate).** The interactive gate is a **same-turn pause** implemented by blocking inside the `exit_plan_mode` tool's `execute()` method itself — not by a harness-level hook that observes the tool-result externally. Since tools return Promises and the agent waits for every tool result before proceeding, `exit_plan_mode.execute()` in interactive TUI mode runs: (1) persist plan file + compute `planHash`; (2) emit `plan_drafted` + `plan_file_written` markers; (3) `await waitForPlanApproval(session)` — a Promise resolved by the TUI's action callback (T31) carrying one of the four actions; (4) once resolved, emit the corresponding `plan_approved` / `plan_rejected` marker + execute the action's state transition (sandbox lift, etc.); (5) return the tool-result whose `status` field reflects the final gate decision (`"plan_approved"` with `executeAfterApproval`, `"plan_rejected"`, or `"plan_abandoned"`). The agent's `AgentSession.prompt()` loop is thus naturally paused by the unresolved tool-result Promise — no SDK hook or private `_emit` path needed. On `reject`, feedback is injected as a **system message appended to the session's message array** (which the agent's next turn-iteration sees), then the tool either returns an appropriate `plan_rejected` status so the agent immediately redrafts, OR `exit_plan_mode` re-opens a drafting loop internally before returning. (Impl detail; both achieve same-turn replan semantics because the tool never returns a final execute-path status.) On caller disconnect, the Promise is rejected, the tool returns `{status: "plan_abandoned", reason: "caller_disconnected"}` and the harness has already emitted `plan_rejected {action: "abandon", feedback: "caller_disconnected"}`. Headless `-m` mode does NOT execute the `await waitForPlanApproval` path (there's no gate per PM-4) — it returns immediately after step 2 with `plan_approved {auto: true, executeAfterApproval: true}`. **PM-2 tool-result semantics revised**: in interactive TUI with this mechanism, the tool-result IS authoritative for the final gate decision (the tool can't return until the user acts). In headless, the tool-result is still "drafting complete" and markers remain the canonical signal. Either way, markers emitted before the tool returns give observers real-time progress.

**Subagents** — per PM-9, out of v0.4.4 scope:
- `delegate` short-circuits with `plan_mode_restricted` when the parent is in plan mode. Subagents do not see `enter_plan_mode` / `exit_plan_mode` in their tool list. The approval-gate mailbox + `awaitingPlanApproval` task state + `plan_approval_request/response` transport are v0.4.5 work.

### 4.5 Blocker policy

**Unrecoverable blocker classifier (harness contract, not agent judgment).** The harness — not the agent — decides when a tool result triggers replan. Classification is deterministic and keyed off the **actual result envelopes** produced by the existing MCP tools (verified against `plugin/klayoutclaw_server.lym`, `tools/route_worker.py`, `tools/evaluate_worker.py`).

**Envelope recap (for the tools classified below only: `klayout_native_auto_route`, `klayout_native_evaluate_design`, `klayout_native_execute_script`, `klayout_native_save_layout`).** Bare plugin-RPC names are permitted in the Inspect/Pattern columns of the classification table because those patterns match payload fields emitted by the plugin-side code (not text the agent's tool-layer sees). §2.1 permits this as a plugin-envelope discussion carve-out. KLayout MCP tool calls return HTTP 200 with an MCP `tools/call` result. Two surface shapes appear:
- **Success envelope.** `{"content": [{"type": "text", "text": <json-string>}]}` where the text is a JSON-encoded tool-specific payload (e.g. `{"status": "success"|"partial"|"failed"|"dry_run", ...}` for `auto_route`).
- **Exception envelope.** `{"content": [{"type": "text", "text": <error-text>}], "isError": true}` — produced by the plugin's generic `try/except` around `handler(tool_args)` (`klayoutclaw_server.lym:1686-1708`) when the handler raises any Python exception, AND by the server-busy path (`:1673-1682`) when a second tool-call arrives while another is running.

HTTP 5xx is never emitted — all exceptions are caught and surfaced as `isError: true` under HTTP 200. **Note:** some other KLayout MCP tools (e.g. `close_layout_view`) return plain `{"status": "error", "error": ...}` inside the success envelope without `isError: true`. Those shapes are **out of scope for v0.4.4 blocker classification** — the table below covers only the four tools above. Adding new tools to the classifier is a spec change per the extensibility clause.

**Classification table (normative for v0.4.4):**

| Tool | Inspect | Pattern | Classification |
|------|---------|---------|----------------|
| `klayout_native_auto_route` / `klayout_native_evaluate_design` / `klayout_native_execute_script` / `klayout_native_save_layout` | `result.isError === true` | `"Tool '<name>' failed: <err>\nTraceback..."` from `klayoutclaw_server.lym:1697` | **unrecoverable** |
| Same 4 tools | `result.isError === true` | server-busy text matching `/Server busy:/` from `klayoutclaw_server.lym:1673-1682` | recoverable (transient scheduler contention; the plan-mode wrapper retries after a short backoff — see `agent/src/planning/sandbox.ts` backgroundable annotation). No `plan_execution_aborted` is emitted. |
| `klayout_native_auto_route` | parsed payload (`JSON.parse(content[0].text)`) | `payload.status === "failed"` | **unrecoverable** |
| `klayout_native_auto_route` | parsed payload | `payload.status === "partial"` AND any entry in `payload.errors` does NOT start with `"auto_map_resolution"` (see `route_worker.py:743-747`; auto-map notes are informational, not failures) | **unrecoverable** |
| `klayout_native_auto_route` | parsed payload | `payload.status === "success"` OR (`"partial"` with only `auto_map_resolution*` notes) | recoverable (agent may continue) |

| `klayout_native_evaluate_design` | parsed payload | `payload.overall >= 0.30` | recoverable (agent reads `next_step_suggestion` as advisory text only — the string is free-form guidance like `"Re-read the task instruction..."`, not a machine-classifiable failure signal; see `evaluate_worker.py:_build_next_step`) |
| `klayout_native_execute_script` | `result.isError` | covered by the first row above | **unrecoverable** |
| `klayout_native_save_layout` | `result.isError` | covered by the first row above | **unrecoverable** |
| Anthropic API 429 / 529 | SDK layer, not tool result | any | NOT a blocker — the SDK retry queue handles it transparently; no `plan_*` marker fires |

**Harness contract.** On an unrecoverable classification, the harness emits `plan_execution_aborted {reason, tool, pattern, replan_count}` where `pattern` is a short identifier drawn from the normative set: `"isError:true"`, `"auto_route:failed"`, `"auto_route:partial_with_errors"`, `"evaluate_design:low_overall"`. On a recoverable classification, no `plan_*` marker fires and the agent continues.

**Agents MUST NOT self-classify.** If the harness does not emit `plan_execution_aborted`, the agent proceeds; if it does, the agent yields to the replan gate (PM-6).

**Tools outside the classifier table (normal-error path).** Tool failures from any tool NOT in the 4-tool classifier table above — including VC tools (`klayout_native_vc_*`), domain skill tools (`klayout_<group>_*`), and other native tools (`klayout_native_create_layout`, `klayout_native_screenshot`, `klayout_native_route_inspect`, `klayout_native_validate_pixel_size`, `klayout_native_close_layout_view`) — do NOT trigger the replan loop. Their errors surface as ordinary tool-result failures the agent handles in-turn (retry, adjust, or continue). This is deliberate: the replan loop is reserved for "plan-invalidating" failures from the 4 core geometry/evaluation tools that represent large physical-design steps. Minor tool failures (e.g. a `vc_tag` name collision) shouldn't trigger a full replan. If a v0.4.5 workflow needs broader replan coverage, it's a spec extension to this table.

**Extensibility.** New classification rules MUST be added to this table (spec change) before the harness honours them. No ad-hoc agent-side classification is permitted.

On blocker (replan cap is **3 replans per original user turn**; the 4th attempt triggers hard-fail):
1. Emit `plan_execution_aborted` with `reason` (intermediate marker — does NOT terminate the turn; `plan_done` is reserved for the single terminal event).
2. Increment `replan_count` (scoped to the current user turn; **reset to 0 at the start of each new user turn** — i.e. each new prompt submission clears the counter. Not tied to PM-12 session-cache lifecycle).
3. If `replan_count <= 3`: transition to `plan_drafting` with blocker context injected as a system message. Emit `plan_replan` (see §4.6). Agent redrafts; approval gate re-runs; the same plan-slug file is overwritten (PM-11).
4. If `replan_count > 3`: emit `plan_done` with `status: "failed"` and the cumulative blocker history in `reason`, return control to the user. No automatic replans in the same user turn.

### 4.6 Transcript-marker schema

All markers are namespaced `plan_*`. Unknown markers are silently ignored by consumers (forward-compat, per §2).

```
{type: "plan_drafted",            plan: string, planHash: sha256-hex,
                                  planLengthChars: int, planSlug: string,
                                  planFilePath: string, replan_count: int, ts}
{type: "plan_file_written",       planFilePath: string, planHash: sha256-hex,
                                  bytes: int, ts}
{type: "plan_approved",           auto: bool, executeAfterApproval: bool, ts}
{type: "plan_rejected",           feedback: string,
                                  action: "reject" | "abandon", ts}
{type: "plan_executing",          planHash: sha256-hex, ts}
{type: "plan_execution_aborted",  reason: string, replan_count: int,
                                  tool: string, pattern: string, ts}
{type: "plan_replan",             replan_count: int, prev_reason: string, ts}
{type: "plan_done",               status: "ok" | "failed",
                                  reason?: string, ts}
```

Field and marker notes:
- `planHash` is `sha256(utf8Bytes(plan))`, lowercase hex. The same hash appears on `plan_drafted`, `plan_file_written`, and `plan_executing`. Any mismatch among the three is a PM-5 integrity violation.
- `planLengthChars` is the JS `String.length` of the plan (code-unit count), matching the semantics of Claude Code's `tengu_plan_exit.planLengthChars` (PM-13).
- `planSlug` is the word-slug from PM-11; stable across replans within a session.
- `planFilePath` is the absolute path the plan was written to (for user-facing "your plan is saved at…" messages, mirroring Claude Code's `ExitPlanModeV2Tool` `tool_result` body).
- A `requestId` field on `plan_approved` is NOT part of the v0.4.4 schema. It will be introduced in v0.4.5 when the subagent approval-gate transport (PM-9) and headless approval RPC (OQ-7) ship together.
- `executeAfterApproval` on `plan_approved` distinguishes the two approve-paths: `true` means option 1 (approve & execute, transition to `plan_executing`); `false` means option 2 (approve draft-only, sandbox lifts but no execution — turn ends).
- `action` on `plan_rejected` disambiguates option 3 (`"reject"` — replan loop per PM-6) from option 4 (`"abandon"` — skip replan, exit plan mode immediately). `feedback: "abandoned"` is the canonical sentinel for option 4.
- `plan_file_written` is **new in v0.4.4** — justification: it makes the disk-write observable to consumers (E2E tests can assert the file exists with the expected hash without reading the filesystem), and it's the natural hook for a future `persistFileSnapshotIfRemote`-style remote-session transcript snapshot.
- `plan_execution_aborted` is **new in v0.4.4** — justification: separates intermediate replan-triggered aborts from terminal markers. On the execute path, `plan_done` is emitted at most once with `status ∈ {"ok", "failed"}`; every intermediate failure goes through `plan_execution_aborted` followed by either `plan_replan` (continue) or `plan_done: failed` (give up). Non-execute paths (`approve_only`, `abandon`) terminate via their own markers without ever emitting `plan_done`. The full invariant is: **exactly one terminal marker per turn, chosen from {`plan_done`, `plan_approved{executeAfterApproval: false}`, `plan_rejected{action: "abandon"}`}** — see §4.2 state invariants.
- `plan_replan` is **new in v0.4.4** — justification: distinguishes a replan loop entry from an initial draft in T4-style marker-ordering assertions and makes the blocker trail greppable without having to reconstruct it from adjacent `plan_execution_aborted` / `plan_drafted` pairs.

### 4.7 Marker transport

Transcript markers (`think_recorded`, `plan_*`) are emitted through qlaybot's existing **session event** pipeline — no new transport is introduced.

**Producer.** qlaybot v0.4.4 introduces a **qlaybot-owned `TranscriptMarkerEmitter`** (`agent/src/events/marker-emitter.ts`, new file) implementing the EventEmitter pattern with a single event `"marker"`. This is independent of `@mariozechner/pi-coding-agent`'s closed `AgentSessionEvent` union — v0.4.4 does NOT extend the SDK's event types, avoiding any private-API / upstream-patch dependency. The harness (`agent/src/agent.ts` wrappers + plan-mode state-machine shim in `agent/src/planning/`) holds a reference to the per-session `TranscriptMarkerEmitter` and calls `emitter.emit("marker", marker)` when a marker is produced.

**Producer roles** (single authoritative list):
- **Harness-owned plan-mode state-machine wrapper** emits all 8 `plan_*` markers (`plan_drafted`, `plan_file_written`, `plan_approved`, `plan_rejected`, `plan_executing`, `plan_execution_aborted`, `plan_replan`, `plan_done`).
- **`thinking` tool-factory (exception)** emits `think_recorded`. This is a deliberate tool-layer carve-out — the tool's whole purpose is to surface a reasoning step, and coupling its emission to the harness would require the harness to inspect tool-call arguments (fragile). The `thinking` tool is therefore the **only** tool-layer producer; all other tools (including plan-mode tools and future KLayout tools) MUST route marker emission through the harness.
- **TUI code** is never a producer — only a subscriber.

**Event shape.** The emitter's `"marker"` event delivers a single argument: the marker object (tagged union per §4.6 + TH-8). Canonical timestamp lives on `marker.ts` (iso8601); no wrapper re-adds a `ts` field. qlaybot's existing `subscribeToSession(session, callbacks)` (`agent/src/events.ts`) is extended to accept an `onTranscriptMarker?: (marker) => void` callback and wire it to the emitter's `"marker"` event. Consumers who need the emitter directly can reach it via `getTranscriptMarkerEmitter(session)` (a small helper keyed by `WeakMap<AgentSession, TranscriptMarkerEmitter>` — parallels PM-12's `PlanSlugCache` pattern).

**Persistence.** The emitter has two built-in subscribers that are **independent** (neither one feeds the other). Both wrap the marker in the **existing `HistoryEntry {timestamp, type, data}` envelope** (`agent/src/history.ts:17`) — one canonical wire shape across both sinks:
1. **`InteractionHistory`** (class in `agent/src/history.ts`, exports `appendTranscript(entry: HistoryEntry)`) — subscribes directly to the `TranscriptMarkerEmitter`. The `HistoryEntry.type` union (currently `"user_prompt" | "agent_response" | "agent_thinking" | "tool_call" | "tool_result" | "error"`) gains a new variant `"transcript_marker"`. The entry is `{timestamp: marker.ts, type: "transcript_marker", data: marker}`. Markers land in `~/.qlaybot/history/<dateDir>/<sessionId>/*.jsonl`.
2. **`VerboseTranscriptWriter`** (`agent/src/verbose-transcript.ts`) — subscribes **directly** to the same `TranscriptMarkerEmitter`, **not** to `InteractionHistory`. The current `VerboseTranscriptWriter` implementation must be updated if it mirrors history; each subscriber is authoritative for its own sink. Markers are written in the **same envelope** `{timestamp: marker.ts, type: "transcript_marker", data: marker}` to `<workspaceDir>/qlaybot-transcripts/<sessionId>-<timestamp>.jsonl` when the session was started with `--verbose`. Because both subscribe to the same emitter with the same envelope-wrapping logic, T43(b) byte-equality holds; because they are independent, neither duplicates nor drops lines relative to the other.

**Consumers.**
- **TUI** (`agent/src/tui/components/App.tsx`) subscribes via `subscribeToSession(session, {onTranscriptMarker: …})` using the new callback. Renders per §7.5 (ThinkingIndicator for `think_recorded`; distinct styling per `plan_*` state).
- **JSON-RPC callers (`-m` mode)** receive markers as `transcript_marker` events on the existing JSON-RPC event stream. `agent/src/rpc.ts` already forwards session-layer events (`tool_use`, `tool_result`, `thinking`, `content_delta` at `:214-217`) to the JSON-RPC output; v0.4.4 adds an equivalent forward by subscribing to `getTranscriptMarkerEmitter(session)` and calling `sendEvent("transcript_marker", marker)` on each event. The wire-level JSON carries the marker object directly (no envelope).
- **E2E tests** assert against the history JSONL (`InteractionHistory` sink) AND/OR the verbose-transcript JSONL AND/OR the live JSON-RPC stream — see T4, T19, T37, T43.

**Canonical timestamp.** `marker.ts` is the authoritative value. Outer wrappers (history entry `timestamp`, JSON-RPC `transcript_marker` event delivery time) must either copy it verbatim or omit their own `ts` — they must NOT diverge.

**Forward-compat.** Unknown `marker.type` values are silently ignored by all consumers (per §2 invariant). Adding new markers in v0.4.5+ requires only new type tags in the union; no transport change.

### 5.2 Components

#### 5.2.1 Serializer (`plugin/klayoutclaw_vc/serializer.py`)

| ID | Requirement | Priority |
|----|-------------|----------|
| DM-1 | **Deterministic serialisation**: identical `pya.Layout` → identical bytes, every time. Cells emitted in sorted order; shapes within a cell ordered by `(layer, datatype, bbox-lexicographic)`. | P0 |
| DM-2 | **GDSII ↔ text round-trip**: lossless across polygons (with holes), paths, text, SREF, AREF, labels, properties, layers. | P0 |
| DM-3 | **Code generation**: export any snapshot as executable pya Python that reconstructs the layout. Format = pya (KLayout Python API); no gdsfactory support in v0.4.4. | P1 |
| DM-4 | **Transient → persistent migration**: memory-mode history materialises to disk `.gds.vc/` on first `save_layout`. | P0 |
| DM-5 | **Crash recovery (disk-backed sessions only).** On reopening a `.gds` that has a sibling `.gds.vc/` directory, detect uncommitted snapshot data (e.g. a git index with staged-but-uncommitted content, or a dangling `.gds.vc/RECOVERY/` journal written by `auto-checkpoint-on-save`) and offer recovery on load. Memory-mode / pre-save sessions are **out of scope** — a crash before the first `save_layout` leaves no durable state, so no recovery is possible; the agent or user restarts from a clean layout. Implementation note: the recovery journal is flushed to `.gds.vc/RECOVERY/journal.json` on every `vc_checkpoint` call AFTER the git commit succeeds, so a crash between checkpoint and save can still recover the last good checkpoint. | P1 |

**Interface contract:**
```
serialize(layout: pya.Layout) -> str     # deterministic
deserialize(text: str) -> pya.Layout
to_pya_code(layout: pya.Layout) -> str   # DM-3
```

#### 5.2.2 Repo backend (`plugin/klayoutclaw_vc/repo.py`)

Thin wrapper over a real git repo inside `<gds_file>.gds.vc/`. Before first save, the repo lives in an in-memory or tmpdir-backed form; first save materialises.

| ID | Requirement | Priority |
|----|-------------|----------|
| RB-1 | **Automatic repository detection on file open** (implements VC-1). When KLayout opens a `.gds` file, the VC plugin inspects the sibling `<file>.gds.vc/` path. If present and a valid git repo, `init(gds_path)` returns a handle bound to that repo. If absent, `init(gds_path)` returns a handle bound to a transient in-memory (or tmpdir) repo that materialises on first save (DM-4). Neither path prompts the user; the status chip (UI-1) communicates the resulting mode. | P0 |
| RB-2 | **Atomicity.** `checkpoint(layout, message, tags=[])` writes to a git index then commits; partial failure leaves the repo unchanged. On atomicity failure the tool returns a structured error; no in-memory state is mutated. | P0 |
| RB-3 | **Memory-mode lifecycle.** A transient in-memory repo is backed either by an ephemeral `tempfile.mkdtemp()` git directory or an in-process representation equivalent to one. On `save_layout` (DM-4), the backend copies/renames the transient repo into `<file>.gds.vc/` atomically; the `RepoHandle` remains valid across the migration. | P0 |
| RB-4 | **Handle invariants.** A `RepoHandle` outlives individual tool calls but is reset on layout close or on a fresh `init(gds_path)` call. `status()` MUST reflect the current on-disk state, not cached values; dirty detection compares the serialised form of the current `pya.Layout` against the HEAD snapshot using DM-1's deterministic serialisation. | P1 |

**Interface contract:**
```
init(gds_path) -> RepoHandle
checkpoint(layout, message, tags=[]) -> sha
history(limit?, branch?) -> [{sha, message, ts, tags, branch, stats}]
checkout(ref) -> None               # restores layout in the current view
diff(ref_a, ref_b) -> {
  added_polygons, removed_polygons, moved_polygons,
  layer_stats, bbox_delta, polygon_count_delta
}
branch(op, name, from_ref?) -> None | [names] | {ok: False, conflicts: [...]}   # op ∈ list/create/switch/merge; merge returns the conflict variant on overlap
tag(name, ref?) -> None
export(ref, format) -> bytes | str  # format ∈ {"gds", "pya"}
status() -> {branch, dirty, last_checkpoint_ts, pending, mode}   # mode ∈ {"disk", "memory"}
```

**Atomicity:** checkpoint writes to a git index then commits; partial failure leaves repo unchanged.

#### 5.2.4 MCP tools (registered in `plugin/klayoutclaw_server.lym`)

All follow existing JSON-RPC 2.0 over HTTP on `127.0.0.1:8765`. The "Tool" column below lists the **plugin-level bare name** (as registered by the server). **Agent-interface requirements** (mirrors canonical §3.4 so each MCP-n is a first-class requirement in this spec, not only a mapping column):

| ID | Requirement | Priority |
|----|-------------|----------|

### 5.3 Non-functional requirements

| Dimension | Target |
|-----------|--------|
| Checkpoint latency | < 2 s for layouts up to 100 MB GDSII |
| History load | < 1 s for repos with < 100 commits |
| Checkout responsiveness | < 1 s for layout reload + viewport refresh |
| Data integrity | Zero geometry loss across serialise → deserialise; checksum-verifiable |
| Graceful degradation | All VC failures leave KLayout functioning as a normal editor |
| Zero configuration | Works out-of-the-box; no manual git setup required |

### 5.4 Scope & boundaries

**Included:**
- Single-user, single-machine workflow.
- GDSII primitives: polygons (with holes), paths, text, SREF, AREF.
- KLayout Python API-based implementation.
- Git-compatible storage format (external `git` tools can operate on `.gds.vc/`).

**Excluded (explicitly):**
- Multi-user concurrent editing.
- Remote push/pull to GitHub/GitLab.
- Automatic binary merge for overlapping geometry (conflicts reported, manual resolution).
- OASIS as the primary serialisation format (GDSII primary; OASIS via conversion).

## 6. Cross-track integration

All cross-track behaviour is mediated by **system-prompt guidance only**. No code-level hooks wire one feature into another.

Prompt additions (wording finalised in impl plan):

> **Checkpoint discipline during plan execution.** Before any destructive MCP call during `plan_executing` (`klayout_native_save_layout`, `klayout_native_auto_route`, `klayout_native_execute_script` that mutates geometry), consider calling `klayout_native_vc_checkpoint` with a short message so the user can roll back. If `klayout_native_vc_status` returns `vc not initialized`, skip this guidance silently.

> **Recovery on blocker.** If a `plan_executing` step fails unrecoverably, consider `klayout_native_vc_checkout` to the last good checkpoint before re-drafting. Record the decision via `thinking`.

> **Reasoning discipline.** Use `thinking` before destructive MCP calls, when resolving ambiguity, and when choosing between approaches. Reference the active VC branch/checkpoint when it's load-bearing.

Invariant: any of the three features must remain individually usable if the others are absent (e.g., `thinking` works in a session where plan mode is never entered and VC is never initialised).

## 8. Error handling & failure modes

### 8.1 Track 1

| Failure | Handling |
|---------|----------|
| `thinking` called with empty `thought` | Tool returns validation error; agent receives schema-level failure and retries with content. No state change. |
| `thinking` called during `plan_drafted` | Harness rejects the call with a state-violation error; agent must wait for approval. |
| Approval prompt receives unparseable input | Treat as rejection; capture raw text as `feedback`. |
| `autoApprovePlans: false` set in `-m` config | Harness logs a warning `"autoApprovePlans=false is v0.4.5 (OQ-7); treating as true"` and proceeds with auto-execute. No gate opens. |
| Replan loop exhausted | Emit `plan_done: failed`; surface cumulative blocker history; hand back to user. |
| Plan-text tampering detected between `plan_drafted` and `plan_executing` entry | Emit `plan_rejected {action: "abandon", feedback: "plan integrity violation"}` as the turn's terminal marker. Detection is scoped to pre-execution per PM-5; post-entry tampering is out of v0.4.4 scope (injected bytes are already in memory and no revalidation cadence exists). |

### 8.2 Track 2

| Failure | Handling |
|---------|----------|
| `vc_init({mode: "auto"})` called with no writable directory for sidecar | Fall back to memory mode; warn in the tool response (durability-best-effort per RB-1). |
| `vc_init({mode: "disk"})` called with no writable directory for sidecar | Return `{ok: false, reason: "disk mode requested but sidecar not writable: <path>"}`. Do NOT fall back to memory — the caller explicitly asked for disk-durability. |
| `vc_checkpoint` mid-git-commit failure | Atomic: repo state unchanged; tool returns error with git stderr. |
| `vc_checkout` to a ref that doesn't exist | Reject with error; layout unchanged. |
| `vc_diff` between incompatible refs (e.g., different top cells) | Return structured diff with a `warning` field; do not fail. |
| `vc_branch merge` detects overlap conflict | Return `{ok: false, conflicts: [...]}`; leave both branches untouched. |
| Sidecar repo corrupted on load | Log error, continue in memory mode, offer repair via UI dialog. |
| Crash with uncommitted snapshot data | On next KLayout startup + same-file open, UI offers "Recover lost work?" dialog (DM-5). |
| VC unavailable but prompt guidance suggests `klayout_native_vc_checkpoint` | Agent's call returns `vc not initialized`; agent proceeds without checkpoint. No plan-mode failure. |

### 8.3 Graceful degradation

If Track 2 ships but VC is not initialised for the current layout, `klayout_native_vc_*` MCP tools return a uniform `{ok: false, reason: "vc not initialized"}` response — **with two normative exceptions**: (1) `klayout_native_vc_init` is always callable and transitions from "not initialised" to initialised (its whole purpose); (2) `klayout_native_vc_status` is always callable and returns the `{ok: false, reason: "vc not initialized"}` response directly (per MCP-8), so callers can probe state safely. RB-1 (auto-detection on open) makes "not initialised" rare in practice: opening a `.gds` installs a `RepoHandle` (memory mode if no sidecar), after which `vc_status` returns `{ok: true, mode: "memory"}`. The `{ok: false}` state applies only when no layout has been opened yet or when `RepoHandle` construction itself failed. Track 1 features continue to work unchanged regardless of VC state.

## 9. Success criteria — E2E tests

### 9.1 Track 1 (release-blocking)

- **T1 — thinking tool wiring.** Start qlaybot, send a multi-step geometry task ("design a 3-contact Hall bar"). Assert:
  (a) `thinking` appears in `tools/list` (hard gate);
  (b) transcript contains ≥1 `think_recorded` marker before any destructive MCP call (**soft assertion** — TH-5/TH-12 define `thinking` as advisory / non-forcing, so missing calls emit a CI warning, not a test failure; release gate is not blocked by this clause);
  (c) each `thinking` tool result echoes the input `thought` verbatim (per TH-3), with no additional side effects (no file writes, no MCP calls, no state mutation) (hard gate);
  (d) task completes successfully (hard gate).

- **T2 — Plan-mode execution happy path.** Send a task in plan mode with a concrete goal ("add 4 bonding pads at corners"). Assert:
  (a) agent calls `enter_plan_mode({task, reason?})` and gets `status: "plan_mode_active"` with a non-empty `plan_file` path;
  (b) agent writes a plan into that file using the `plansDir`-scoped `write`/`edit` tools (the active plan file is a convention, not a hard constraint — §4.2);
  (c) agent calls `exit_plan_mode({approved: true})`;
  (d) harness surfaces the 4-option approval gate (TUI) or self-approves via `approve_execute` (`-m`);
  (e) on `approve_execute`, session auto-transitions to `plan_executing` without restart;
  (f) MCP geometry tools fire in the same session;
  (g) final layout matches the plan via `klayout_native_evaluate_design`.

- **T3 — Plan rejection.** Same setup as T2, user rejects. Assert:
  (a) agent stays in plan mode;
  (b) no MCP tool calls fire between `plan_rejected` and the next `plan_drafted`;
  (c) agent redrafts **within the same user turn** with feedback in scope (per §4.2: `plan_rejected {action: "reject"}` is non-terminal and re-enters `plan_drafting` in the same turn; no terminal marker is emitted on this branch yet).

- **T4 — State-marker ordering.** Assert marker order per path (all paths share the `plan_drafted → plan_file_written` prefix):
  (a) **Execute path** (`approve_execute`): `plan_drafted → plan_file_written → plan_approved{executeAfterApproval: true} → plan_executing → plan_done(status="ok")`.
  (b) **Draft-only path** (`approve_only`): `plan_drafted → plan_file_written → plan_approved{executeAfterApproval: false}` (terminal — no `plan_done`).
  (c) **Reject → redraft**: `plan_drafted → plan_file_written → plan_rejected{action: "reject"} → plan_drafted …` (back to drafting; terminal marker not yet reached).
  (d) **Abandon path** (option 4 OR `exit_plan_mode({approved: false})` shortcut): `plan_rejected{action: "abandon"}` as the terminal marker; in the gate-option-4 case preceded by `plan_drafted → plan_file_written`; in the shortcut case, emitted directly with no `plan_drafted` preamble.
  (e) **Replan path**: `plan_drafted → … → plan_executing → plan_execution_aborted → plan_replan → plan_drafted → …`.
  (f) **Terminal invariant** (§4.2): exactly one marker from `{plan_done, plan_approved{executeAfterApproval: false}, plan_rejected{action: "abandon"}}` appears per user turn. Assert across all five sub-scenarios.

- **T5 — Replan loop guard.** Induce an unrecoverable blocker on every attempt (e.g., request a route that is physically impossible). Assert:
  (a) agent emits `plan_execution_aborted` + `plan_replan` on attempts 1, 2, 3 (no `plan_done` emitted yet);
  (b) on the 4th aborted attempt, emits terminal `plan_done` with `status: "failed"`;
  (c) exactly one terminal marker appears in the transcript across the whole replan loop (a `plan_done {status: "failed"}` on the 4th attempt; never two terminal markers);
  (d) no further replans fire in the same user turn.

- **T6 — Plan integrity (PM-5).** Capture the `planHash` on `plan_drafted`, the `planHash` on `plan_file_written`, and the `planHash` on `plan_executing`. Assert all three match. Tamper the plan-file bytes on disk between `plan_file_written` and `plan_executing` entry → assert terminal `plan_rejected {action: "abandon", feedback: /plan integrity violation/}`. **Post-entry tampering is NOT asserted** — PM-5 explicitly scopes detection to "up to and including `plan_executing` entry"; a test that tampers after entry and expects detection would fail the current contract and is out of v0.4.4 scope.

- **T7 — `thinking` non-interference.** On trivial single-step requests, agent is not forced to emit `thinking` calls (no `think_recorded` markers required). Tool remains available but optional.

- **T8 — Regression (scoped).** All existing v0.4.3 functional, integration, and e2e suites pass unchanged **except** for the suites superseded by the v0.4.4 plan-mode refactor (PM-3, PM-11), which MUST be rebaselined as part of v0.4.4 work. Explicit rebase list:

  (b) `agent/tests/test-plan-mode.sh:74` — globs `plans/plan-*.md` (legacy timestamp filename). Updated to glob the new word-slug filename `plans/*.md` and confirm non-empty, per PM-11.

## 10. Open questions

These must be resolved before the implementation plan is finalised:

- **OQ-1 — Thinking-tool prompt wording.** Exact system-prompt text for §3.4. To be finalised during implementation planning.
- **OQ-2 — VC auto-checkpoint cadence.** Default `autoCheckpointOnSave: true` is decided. Optional time-based auto-checkpoint (every N minutes of dirty edit) — include or defer? Assumption: defer.
- **OQ-3 — VC history-panel thumbnails.** Generate on-demand or cache per-commit? Assumption: on-demand with an LRU cache keyed by sha; size to be set during impl.
- ~~**OQ-4 — Replan blocker classification.**~~ **Resolved** — normative classifier table in §4.5.
- ~~**OQ-5 — `-m` mode transcript streaming.**~~ **Resolved** — §4.7 makes `-m` callers receive live `transcript_marker` events on the existing event stream (same channel as `tool_use`, `tool_result`, `thinking`, `content_delta`). No separate final-JSON delivery; the existing stream is the sole surface.
- **OQ-7 — Headless approval RPC transport (v0.4.5).** The gated headless path (`autoApprovePlans: false`) requires a way for a JSON-RPC caller to submit `{action, feedback?}`. The v0.4.3 RPC surface (`agent/src/rpc.ts:102`) exposes only `initialize`, `prompt`, `get_session_info`, `dispose`, `shutdown` — none accept approval payloads. **v0.4.4 defers the gated headless path entirely** (PM-4 coerces `autoApprovePlans: false` to `true` with a warning; T35 asserts the coercion). Candidate designs for v0.4.5: (a) add a new method `submit_plan_approval` with input `{requestId?, action, feedback?}` and an ack result; (b) extend the existing `prompt` method with a discriminated input (`{kind: "user_prompt", text}` vs `{kind: "plan_approval", action, feedback?}`). Preferred: (a) — new method keeps `prompt` simple and maps cleanly to the existing event stream.
- **OQ-8 — `evaluate_design` blocker threshold (v0.4.5 config).** §4.5 fixes the `evaluate_design` unrecoverable-blocker threshold at `overall < 0.30` in v0.4.4. Making this user-configurable (e.g. `settings.planning.evaluateBlockerThreshold`) is deferred. Preferred v0.4.5 design: a bounded config setting `[0.0, 1.0]` with default `0.30`, validated at startup. v0.4.4 does not expose any knob.
