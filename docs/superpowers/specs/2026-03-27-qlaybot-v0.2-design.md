## 1. Dual-Mode Command System

### Concept

Most commands work in two contexts; `exit` is TUI-only:
- **Shell:** `qlaybot model set sonnet-4-5` — runs, prints output, exits
- **TUI:** `/model set sonnet-4-5` — runs inline, output displayed in TUI

A shared `CommandRegistry` maps command names to handler functions. Each handler receives parsed arguments and a `CommandContext` (session, MCP manager, memory manager, plan manager, background task manager, live session state, config) and returns a `CommandResult`.

### CommandResult Interface

```ts
interface CommandResult {
  output: string;               // text to display
  stateChange?: {               // TUI state mutations
    planMode?: boolean;
    showThinking?: boolean;
  };
  exitCode?: number;            // shell mode: 0 = success, 1 = error
}
```

### CLI Routing (cli.ts)

- `qlaybot` (no args) — TUI
- `qlaybot <command> [args...]` — run command handler, print output, exit
- `qlaybot -m "..."` — JSON mode (existing)
- `qlaybot --mode rpc` — RPC mode (existing)

Existing commands (`onboard`, `uninstall`, `help`) become part of the registry.

### TUI Routing (InputBox)

Lines starting with `/` are intercepted and routed to the registry. Everything else is sent to the agent as a prompt.

### Commands

| Command | Subcommands | Description |
|---------|------------|-------------|
| `model` | `show`, `set <provider/id>`, `list` | Show/switch active model for the current session and persist defaultModel to ~/.qlaybot/config/model.json |
| `mcp` | `status`, `tools [server]`, `reconnect [server]` | MCP server management |
| `config` | `show`, `set <key> <value>`, `reset` | Runtime + persisted config. Writes to ~/.qlaybot/config/model.json and ~/.qlaybot/config/settings.json; applies immediately when possible. Settable keys: `thinking` (level), `model` (default model ref), `memory.maxResults` (auto-recall limit), `memory.maxEntries` (budget per category) |
| `context` | (none) | Show loaded workspace context: lists each file (SOUL.md, WORKFLOW.md, TOOLS.md, RULES.md) with byte size, total system prompt token estimate, and context window usage percent |
| `memory` | `show [category]`, `search <query>`, `clear <category>` | Memory inspection and deletion. `clear` accepts knowledge\|procedures\|preferences\|log and returns deleted entry count |
| `plan` | `enter` (default), `exit`, `status` | Planning mode control |
| `tasks` | (none) | Background task status |
| `help` | `[command]` | Command help, or help for a specific command |
| `exit` | (none) | Graceful shutdown (TUI-only, no-op from shell) |

### /mcp — Dual Client Display

The `/mcp status` output distinguishes KLayout (custom HTTP) from standard MCP servers:

```
MCP Servers:
  klayout (custom HTTP)     * connected   :8765   6 native + 15 domain tools
  instrmcp (HTTP JSON-RPC)  o lazy        :8123   not yet discovered
  filesystem (HTTP JSON-RPC) * connected           12 tools
```

Three states: **connected**, **lazy** (configured, not yet connected), **disconnected**.

`/mcp tools klayout` lists native and domain tools separately. `/mcp tools <server_key>` lists tools for any standard server.

### File Structure

```
src/commands/
  index.ts        # CommandRegistry class + CommandContext + registration
  model.ts        # model [show|set|list]
  mcp.ts          # mcp [status|tools|reconnect]
  config.ts       # config [show|set|reset]
  context.ts      # context
  memory.ts       # memory [show|search|clear]
  plan.ts         # plan [enter|exit|status] — delegates to PlanManager
  tasks.ts        # tasks — delegates to BackgroundTaskManager
  help.ts         # help [command]
  exit.ts         # exit
```

## 2. Thinking Toggle

### Keybinding

`Ctrl+T` toggles thinking visibility in the TUI.

### Display Behavior

| showThinking | Agent State | Display |
|:---:|:---:|---|
| true | actively thinking | Thinking block inline, dimmed/italic, streaming |
| false | actively thinking | `[thinking... 3.2s]` compact indicator, updates live |
| true | done | Full thinking block in message history |
| false | done | Thinking block omitted from rendered output |

### Implementation

- **State:** `showThinking: boolean` in TUI state, default `false`
- **Reducer action:** `TOGGLE_THINKING_VIEW` — flips `showThinking`
- **Data preservation:** Thinking content always captured in reducer regardless of visibility. Toggling mid-stream shows/hides immediately with no data loss.
- **Components:**
  - `InputBox.tsx` — captures `Ctrl+T`, dispatches `TOGGLE_THINKING_VIEW`
  - `MessageList.tsx` — conditionally renders thinking blocks based on `showThinking`
  - `StatusBar.tsx` — shows `[T]` indicator when thinking is visible

### Not In Scope

This toggle does not affect the `--thinking` CLI flag (API-level thinking level). It is purely a display concern.

## 3. Planning Mode

### Concept

A modal state where the agent can reason and explore but cannot mutate the layout or workspace filesystem (bash/write/edit). Memory writes via `memory_save` are allowed.

### State Machine

```
idle --/plan--> planning --/plan exit--> idle
```

### KLayout-Aware Sandbox

**Allowed (read-only):**
- `read`
- `klayout_native_get_layout_info`
- `klayout_native_screenshot`
- `memory_save`
- `memory_search`

**Blocked (mutating):**
- `bash`, `write`, `edit`
- `klayout_native_execute_script`
- `klayout_native_create_layout`
- `klayout_native_save_layout`
- `klayout_native_auto_route`
- All `klayout_geometry_*`
- All `klayout_display_*`
- All `klayout_image_*`
- All `klayout_nanodevice_*`

When a blocked tool is called, the sandbox returns an error result (not a crash):
`"Tool '{name}' is blocked in plan mode. Exit plan mode with /plan exit to execute."`

### System Prompt Injection

Before each `session.prompt()` call, if plan mode is active, prepend this section to the effective system prompt:

```
You are in PLAN MODE. You can read, inspect, reason, and save to memory,
but you cannot modify the layout or workspace files (no bash, write, edit,
or KLayout mutating tools). Write your plan as structured steps.
When the user approves, they will exit plan mode and you can execute.
```

### File Structure

```
src/planning/
  index.ts        # PlanManager — state + sandbox filter factory
  sandbox.ts      # Tool wrapper that intercepts blocked calls
```

`PlanManager` exposes: `enter()`, `exit()`, `isActive()`, `wrapTool(tool)`.

### RPC

`get_session_info` returns live session state: `{ model, thinkingLevel, contextUsage, planMode, backgroundTasks }`.

## 4. Background Tasks

### Concept

Long-running operations run in the background while the agent continues responding. The user can check status via `/tasks`.

### Use Cases

- Nanodevice flake detection pipeline (minutes)
- Auto-route with many pin pairs (30s+)
- Large GDS saves

### BackgroundTaskManager

```ts
interface BackgroundTask {
  id: string;
  name: string;
  status: "running" | "completed" | "failed";
  startedAt: number;
  completedAt?: number;
  result?: unknown;
  error?: string;
}
```

Methods:
- `run(name, fn)` — wraps async function, returns task ID immediately
- `status(id)` — get task state
- `list()` — all tasks with status
- `result(id)` — get result (returns immediately if completed, waits if running)

### Agent Tools

Two new custom tools:
- `background_status()` — list all background tasks with status
- `background_result(id)` — get result of a specific task

v0.2 uses a deterministic allowlist for background execution: `klayout_nanodevice_flakedetect_detect_stack`, `klayout_native_auto_route`, `klayout_native_save_layout`. These return a task ID immediately and are tracked by `BackgroundTaskManager`.

### Slash Command

`/tasks` displays task status in TUI:
```
Background Tasks:
  #1  flakedetect_detect_stack   * running    2m 14s
  #2  auto_route                 v completed  45s     8/8 pairs
```

### TUI

A `BackgroundBar` section in StatusBar shows active task count. Updates via `BACKGROUND_UPDATE` reducer action.

### RPC

`backgroundTasks` is part of the unified `get_session_info` contract above.

### File Structure

```
src/background/
  index.ts        # BackgroundTaskManager
  types.ts        # BackgroundTask interface
```

## 5. Global CLI via npm link

### Current State

`package.json` already has `"bin": { "qlaybot": "dist/cli.js" }`.

### Changes

1. Keep shebang `#!/usr/bin/env node` at top of `src/cli.ts` (already present in v0.1); add a build/test check that `dist/cli.js` preserves it
2. `qlaybot onboard` output includes link setup guidance
3. Document `npm link` in README

### Full CLI Surface (v0.2)

```
qlaybot                               # Interactive TUI
qlaybot -m "..."                      # Single-shot JSON mode
qlaybot --mode rpc                    # RPC mode
qlaybot --plain                       # Plain readline

qlaybot model [show|set|list]         # Model management
qlaybot mcp [status|tools|reconnect]  # MCP management
qlaybot config [show|set|reset]       # Config management
qlaybot tasks                         # Background task status
qlaybot onboard                       # First-time setup
qlaybot uninstall                     # Remove ~/.qlaybot/
qlaybot help [<command>]              # Help
```

### Shell Completions (stretch)

`qlaybot completions` outputs bash/zsh completion script. Nice-to-have, not blocking for v0.2.

## 6. Agentic E2E Tests

### Philosophy

Test the agent as a harness: natural language in, verify outcomes, not tool sequences. The agent decides which tools to use.

### Test Suites

All tests extend the existing `createRPCClient()` pattern in `tests/test-e2e.ts`. Agentic tests use 360s per-test timeouts, RPC call timeout >= 420s, and capture RPC events (`tool_use`/`tool_result`/`thinking`/`content_delta`) for verification.

#### 4a: Slash Commands via RPC

| Test | Prompt | Verification |
|------|--------|-------------|
| /help lists commands | `/help` | response contains "model", "mcp", "plan" |
| /model shows current | `/model` | response contains model name |
| /mcp shows status | `/mcp status` | response contains "klayout" and connection state |
| /memory shows entries | `/memory show knowledge` | response contains category content (or empty) |
| unknown slash command errors | `/doesnotexist` | structured command error, no crash |
| malformed args error | `/config set thinking invalid_level` | validation error message |

#### 4b: Planning Mode State

| Test | Steps | Verification |
|------|-------|-------------|
| Enter plan mode | Send `/plan` | `get_session_info` returns `planMode: true` |
| Mutating tool blocked | In plan mode, send "Add a rectangle at origin" | response indicates blocked/plan mode |
| Read-only tool allowed | In plan mode, send "What does the current layout look like?" | succeeds (screenshot/get_layout_info) |
| Exit plan mode | Send `/plan exit` | `get_session_info` returns `planMode: false` |

#### 4c: Sandbox Enforcement

| Test | Steps | Verification |
|------|-------|-------------|
| execute_script blocked | Plan mode, "Run this pya code: print('hello')" | blocked |
| create_layout blocked | Plan mode, "Create a new layout" | blocked |
| screenshot allowed | Plan mode, "Take a screenshot" | succeeds |
| bash/write/edit blocked | Plan mode, prompt requesting file edit or shell command | blocked with plan-mode error |
| Tools unblocked after exit | Exit plan mode, "Create a new layout" | succeeds |

#### 4d: Background Tasks

| Test | Steps | Verification |
|------|-------|-------------|
| Task starts | Trigger backgroundable operation (auto_route or save) | task appears as `running` in `get_session_info` |
| Task completes | Poll `get_session_info` after operation finishes | status transitions to `completed` with `completedAt` |
| Result fetch | Call `background_result(id)` for completed task | returns result data |

#### 4e: Agent Autonomy — Design Task

| Test | Prompt | Verification |
|------|--------|-------------|
| Multi-layer structure | "I need a simple test structure: a 200x50um rectangle on layer 1/0 with a 50x50um contact pad on layer 2/0 centered on top of it" | execute_script readback: L1/0 bbox width=200um, L2/0 bbox width=50um |

No explicit tool names in prompt. Agent decides how to build it.

#### 4f: Multi-Feature Integration

| Step | Action | Verification |
|------|--------|-------------|
| 1 | `/model` | model info shown |
| 2 | "Create a layout called integration_test" | layout created |
| 3 | `/plan` | planMode = true |
| 4 | "I want to add alignment markers at the corners" | agent plans, cannot execute |
| 5 | `/plan exit` | planMode = false |
| 6 | "Now do it" | agent executes plan |
| 7 | verify | get_layout_info shows geometry |

#### 4g: Memory + Auto-Recall

| Step | Action | Verification |
|------|--------|-------------|
| Session 1 | "Remember that our standard hall bar uses layer 1/0 for mesa and layer 3/0 for contacts" | memory saved |
| Session 2 | "What layers should I use for a hall bar?" | response mentions 1/0 and 3/0 (auto-recall) |
