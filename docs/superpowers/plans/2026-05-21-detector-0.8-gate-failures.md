## HM07 Combine-Layer Bug Diagnosis

**Summary:** The graphene detector's default cluster (cluster_id=0) outputs 106 px for HM07 on the top-part image. This value is below the 500 px `min_area` guard in `keep_largest_n` (transform.py L187–189), so `keep_largest_n` returns a zero mask. The `_detect_dropped_stage` check then raises `MaskDroppedError("graphene", "keep_largest", ...)` which triggers `sys.exit(3)`, killing the entire `transform.py` subprocess and aborting the combine step.

**Trigger chain:**
1. `graphene.py --cluster-id 0` on HM07 top_part → 106 px output (wrong cluster; correct cluster is 34 → 82 092 px from Phase 7 agent run)
2. `transform.py`: warp → 106 px → `morph_clean(close_k=15, open_k=7)` removes fragments → `keep_largest_n(n=1, min_area=500)` → 0 px (below guard)
3. `_detect_dropped_stage` detects the zero-out → `MaskDroppedError` raised → `sys.exit(3)`

**This is NOT a bug in transform.py.** The 500 px minimum and the MaskDroppedError are working as designed — they prevent a single-pixel noise artifact from producing a spurious contour. The root cause is that the graphene detector's cluster-0 default is selecting background signal on HM07. The agent in the Phase 9 run chose cluster_id=5 (217 px), also below the guard; it navigated the exit(3) and built result.gds via a fallback path that used the wrong graphene contour (graphene IoU=0.001).

**The Phase 7 agent run used cluster_id=34 (82 092 px) which correctly identifies the graphene flake.** Graphene cluster selection on HM07 is intrinsically difficult: the PDMS-substrate top image has a very large number of K-means clusters with similar photometric properties, and the correct one (rank 34) is not surface-level distinguishable.

**Fix (for Phase 10):** The graphene detector's `--cluster-id 0` default is not a reliable choice when the correct flake is at a high rank. Options:
1. Add a confidence metric that scores candidate clusters by their spatial containment within the footprint mask (high containment + appropriate area → good candidate)
2. Lower the `min_area` guard from 500 px → 200 px to prevent exit(3) on marginal detections, and treat sub-200 px graphene as "low confidence, keep trying clusters"
3. The combine layer's `sys.exit(3)` is too aggressive when the failure is graphene-only — consider degrading gracefully (omit graphene polygon, write a warning flag) rather than killing the entire pipeline

## Failure Prioritization

Failures are grouped by root cause. Listed in recommended fix priority order (highest impact first).

### Priority 1: Graphene detector cluster selection (fixes ≥ 10 stacks)

**Stacks affected:** ml09, ml11 (xfail), ml14, AH03, AH05, AH06, AH07, HM05, HM06, HM07, QH06, QH12

**Pattern:** Graphene IoU ≤ 0.537 on 12 of 17 non-xfail stacks. The detector selects the wrong K-means cluster as the graphene flake in most cases. The correct cluster is visually distinguishable in the candidate panel but often has a higher rank than cluster_id=0.

**Evidence:** Agent cluster picks vs. IoU:
- ml09: cluster 8 → IoU=0.273
- AH03: cluster 2 → IoU=0.270
- AH05: cluster 1 → IoU=0.272
- AH07: cluster 0 (default, no retry info) → IoU=0.000
- QH06: cluster not recovered → IoU=0.000

The graphene detector (`graphene.py`) uses K-means with 40+ clusters and ranks them by a scoring function that combines size, contrast, and location. On substrates with complex textures (AH/HM/QH series), the correct graphene flake is not reliably at rank 0–2. The scoring function needs a footprint-containment term: flakes that are highly contained within the top-alignment footprint are graphene candidates; flakes outside it are background.

**Estimated impact if fixed:** Would resolve the graphene=0 failures on AH07, QH06, and likely clear the 0.27–0.28 range on ml09, AH03, AH05 to > 0.5.

**Files to change:** `skills/nanodevice_flakedetect_detect/scripts/graphene.py`

### Priority 2: Graphite detector spatial accuracy (fixes ml04, QH07, QH12, HM05/HM06)

**Stacks affected:** ml04 (graphite=0.693), QH07 (graphite=0.000), QH12 (graphite=0.009), HM05 (0.089), HM06 (0.039)

**Pattern A — ml04:** Graphite input 660 px grows to 42 849 px post-keep_largest in combine. The graphite contour is correctly located but morphological inflation in transform.py makes it much larger than GT.

**Pattern B — QH07/QH12:** graphite IoU ≈ 0, suggesting the detector identified a completely wrong region or the transform step placed it incorrectly.

**Pattern C — HM series:** All HM graphite IoUs < 0.1, consistent with a fundamental detector mismatch on HM-substrate images (possibly different illumination/color balance).

**Files to change:** `skills/nanodevice_flakedetect_detect/scripts/graphite.py`

### Priority 4: HM series alignment quality (fixes HM08, HM11)

**Stacks affected:** HM08 (top_hbn=0.424, `quality=fail (fwd_chamfer)`), HM11 (top_hbn=0.377, `quality=borderline`)

**Pattern:** The top-alignment (PDMS→SiO2) step failed on HM08 and is marginal on HM11. Since top_hBN is the footprint mask from alignment, a bad alignment directly propagates to a bad top_hBN IoU. All other materials also suffer because the footprint mask gates the graphene transform.

**Root cause:** Chamfer alignment with scale=1.23 (HM08) and scale=0.79 (HM11) — both are extreme scale values outside the typical 0.9–1.1 range, suggesting the sweep found a local minimum rather than the true correspondence.

**Note:** This is an alignment pipeline issue, not a detector issue. The alignment artifacts are pre-computed and stored at `/Volumes/RandomData/harbour-workspace/qlaybot/detect/HM*/output/align/`. Fixing HM08/HM11 requires re-running the alignment step with better initialization or cost function, outside the scope of detector de-tuning.

---

### Priority 5: combine `sys.exit(3)` escalation (hardens pipeline for all stacks)

**Stacks affected:** HM07 (pipeline failed on graphene, recovered with wrong contour)

**Issue:** When any material hits `MaskDroppedError`, `transform.py` calls `sys.exit(3)`, killing the entire pipeline. An agent can recover by trying different cluster_ids, but if all retries fail, no result.gds is produced. A more resilient design would allow graphene to be omitted (with a warning flag) rather than blocking all other materials.

**Files to change:** `skills/nanodevice_flakedetect_combine/scripts/transform.py` (degraded-mode handling only — do NOT change min_area or detector scoring)

## Phase 10 Recommended Action Plan

1. **graphene.py: footprint-containment scoring** — Add a `spatial_score` term to the candidate ranking that measures the fraction of each cluster candidate that falls inside the top-alignment footprint mask. Candidates with > 80% containment are strongly preferred. This eliminates false graphene detections on background substrate.

2. **graphene.py: `min_area` floor** — Consider lowering default min_area guard in the combine step from 500 px → 200 px, and surfacing a `low_area` flag in the sidecar JSON to signal the agent to retry with a different cluster before combining.

3. **graphite.py: substrate-adaptive scoring** — The HM-series failures suggest the graphite scoring function is calibrated to SiO2 reflectance characteristics. Add an adaptive reference: compute the substrate L-channel mode from the image itself rather than using a fixed expected range.

4. **bottom_hbn.py: HM-series robustness** — Investigate HM05/HM06 bottom-part images specifically to identify why the detector selects the wrong region (the IoUs of 0.069–0.144 suggest a completely wrong polygon, not a size issue).

5. **transform.py: graceful graphene degradation** — When `MaskDroppedError` fires for graphene only, write a zero-polygon placeholder and continue rather than `sys.exit(3)`. Gate this on a `--allow-zero-graphene` flag so existing callers are unaffected.

**Key observation:** In Phase 8, some stacks that had passable default-detector graphene outputs (ml09 graphene IoU from held-out: 0.497; AH03: 0.700 approx from Phase 8 scores) were *regressed* by the agent picking a worse cluster. This suggests the agent's visual inspection criterion is not well-calibrated — it is visually selecting clusters that look plausible on screen but don't match the GT polygon boundaries.

This is a fundamental constraint of the current agent prompt: the agent can see the candidate panel but cannot compare to GT, so it uses heuristics (expected size, expected shape) that can fail on novel substrates. The highest-leverage fix is improving the graphene detector's default ranking so cluster_id=0 is correct (or top-3 correct) without requiring visual override.
