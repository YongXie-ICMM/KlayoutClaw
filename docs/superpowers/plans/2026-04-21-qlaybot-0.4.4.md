# qlaybot v0.4.4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.4.4 = `thinking` tool + plan-mode execution + (gated) KLayout version control, per `docs/superpowers/specs/2026-04-19-qlaybot-0.4.4-design.md`.

**Architecture:** Two release tracks on top of v0.4.3. Track 1 (TS agent-side: `thinking` + plan-mode execution) is the must-ship core; Track 2 (Python plugin + new MCP surface: `klayout_native_vc_*`) is release-gated and slips to v0.4.5 on failure. The two tracks are coupled only by a shared transcript-marker event stream and system-prompt text — no hard runtime hooks.

**Tech Stack:** TypeScript (agent `@mariozechner/pi-coding-agent` SDK wrapper, ink/React TUI, vitest, JSON-RPC-over-HTTP); Python (`pya`/KLayout API, git, `tempfile`, embedded Qt via `.lym` autorun macros); Node subprocess bridge unchanged.

**How to use this plan.** Each task names (1) the exact files, (2) the spec clause(s) it discharges (e.g. `TH-3`, `PM-11`, `MCP-4`, `T24(d.3)`), (3) a TDD sequence (failing test → run → implement → run → commit). Code snippets are kept minimal — the spec is the source of truth for behaviour; this plan is the decomposition map. When a step says "implement per §X", read §X in the spec before writing the code.

**Spec clause ↔ task index** is maintained at the bottom (§S: Requirements Traceability) so each requirement has an owner.

### Task 0.2 — Per-session emitter registry helpers (`get`/`set`)

**Files:**
- Modify: `agent/src/events/marker-emitter.ts`
- Test: `agent/tests/test-marker-emitter.ts`

**Spec:** §4.7 "Consumers who need the emitter directly can reach it via `getTranscriptMarkerEmitter(session)`".

**Chicken-and-egg note.** `assembleTools` runs BEFORE `AgentSession` exists (see `agent/src/agent.ts:createDesignSession` flow — the tool map is built, then passed into the SDK's session constructor). So a pure `getTranscriptMarkerEmitter(session)` API is not sufficient — tools need the emitter instance at assembly time, but the `WeakMap<AgentSession, TranscriptMarkerEmitter>` registry can't be keyed until the session exists. Split the API into (i) a constructor-in-`agent.ts` path that creates the emitter up-front and passes it down via `opts.transcriptMarkerEmitter` to `assembleTools`, and (ii) a `setTranscriptMarkerEmitter(session, emitter)` registration call made in `createDesignSession` AFTER the session is built, so that other consumers (RPC, history, verbose) can reach the same emitter by session.

- [ ] **Step 1 — Write failing tests.**
  - (a) `setTranscriptMarkerEmitter(session, e)` then `getTranscriptMarkerEmitter(session)` returns `e`;
  - (b) `getTranscriptMarkerEmitter(differentSession)` returns `undefined` (NOT auto-create);
  - (c) registry keyed by `WeakMap` — dropping the session reference allows GC.
- [ ] **Step 2 — Run test → fail.**
- [ ] **Step 3 — Implement.** Export `getTranscriptMarkerEmitter(session: AgentSession): TranscriptMarkerEmitter | undefined` and `setTranscriptMarkerEmitter(session: AgentSession, emitter: TranscriptMarkerEmitter): void` backed by a module-scoped `WeakMap<AgentSession, TranscriptMarkerEmitter>` (parallels `PlanSlugCache` pattern from PM-12 — Phase 2).
- [ ] **Step 4 — Run → green.**
- [ ] **Step 5 — Commit:** `feat(agent/events): add get/setTranscriptMarkerEmitter WeakMap registry`.

## Appendix — Engineering Notes

**Why the slug refactor happens before the state machine (Phase 2 ordering):** the state machine needs to reuse, truncate, and clear slug-cache entries on each terminal transition. Building the cache first makes the state machine a pure consumer. The alternative order leaves the state machine with TODOs that accumulate risk.

**Why `TranscriptMarkerEmitter` is qlaybot-owned (not an SDK extension):** per §4.7, extending `@mariozechner/pi-coding-agent`'s `AgentSessionEvent` union would make v0.4.4 depend on an upstream patch. A local emitter keeps the SDK surface untouched.

**Why `thinking` is registered in both `NON_MCP` and `ALLOWED_BASE` (Task 1.2):** the deny-by-default allowlist at `agent/src/tools/index.ts:286-319` throws on any tool not covered by one of two sets. `thinking` is agent-built-in, not MCP, but the existing allowlist sets are named after historical categories; the cleanest minimal change is to add `thinking` to both rather than refactor the allowlist. If the allowlist is refactored in v0.4.5, this can collapse.

**Plugin test env.** `tests/test_vc_*.py` runs in conda env `base` (per memory note 2026-03-13: `instrMCPdev` doesn't exist on this machine; `base` has `cv2`, `numpy`, `scipy`, `sklearn`). Plugin tests additionally need `pya` — run them via `klayout -z -nc -r tests/test_vc_*.py` (KLayout scripted mode) OR via the subprocess bridge.

**Commit message prefixes used in this plan.** `feat(agent/<subdir>): …`, `refactor(agent/<subdir>): …`, `test(…): …`, `chore(release): …`. Matches the v0.4.3 conventions in recent commits (`feat: qlaybot v0.4.3 …`, `docs(specs): …`).

**Fail-fast philosophy for the replan classifier (Task 2.15).** The classifier is **deliberately narrow** — only 4 tools produce `"unrecoverable"`. If a tool is missing from the table and the agent stalls, that is a known-accepted cost vs. the risk of false-positive replans on tools whose failure mode is benign. Spec §4.5 "Extensibility" makes broadening it a *spec change*, not an ad-hoc agent call.
